# AI Legal Helper — 소스코드 주석 작성 표준

- 문서 버전: 1.0
- 적용 시점: P2.1부터 신규 작성 및 수정하는 모든 코드
- 적용 언어: Python, TypeScript, React
- 작성 언어: 한국어 (식별자·공식 기술 용어는 원어 유지)
- 규범: **필수**

## 1. 목적과 원칙

AI Legal Helper는 법률 Agent, LangGraph, RAG, 사건·증거 관리, API, UI를 포함하는 장기 프로젝트다. 개발자가 처음 보는 코드를 주석만으로도 추적할 수 있도록 **역할, 처리 흐름, 분기 이유, 데이터 변화, 예외와 설계 의도**를 설명한다.

- **왜(Why)**를 우선 설명하고, 복잡한 **어떻게(How)**를 보완한다.
- 단순 대입이나 자명한 문장을 반복하지 않는다.
- 실제 동작과 주석이 항상 일치해야 한다. 기능 변경 시 관련 주석도 수정한다.
- 확인하지 않은 법률적 사실·출처·구현 상태를 확정적으로 적지 않는다.
- 주석에 API Key, 비밀번호, 개인정보, 상담 원문 등 민감정보를 기록하지 않는다.
- 기존 정상 코드의 무의미한 대규모 수정은 금지한다. 변경하는 코드부터 적용하고 핵심 기존 모듈은 점진적으로 보강한다.

## 2. Python 모듈 머리말 템플릿

주요 Python 파일의 최상단에 다음 Docstring을 작성한다. 해당되지 않는 항목은 `해당 없음`으로 명시하거나 생략할 수 있다.

```python
"""법률 상담 Supervisor 모듈.

[역할]
사용자 상담 요청에 대해 법률 분석 및 검증 단계를 조정한다.

[주요 기능]
- Router/Planner를 호출해 전문 Agent를 선택한다.
- 답변 검증 결과에 따라 종료 또는 제한적 재검토를 수행한다.

[입출력 및 데이터 흐름]
ConsultationState → route → plan → agents → synthesize → verify → final

[주요 의존성]
LangGraph, LLM Gateway, Verification Agent, Trace Context

[설계상 주의]
재검토는 최대 1회이며, 근거 부족을 PASS로 처리하지 않는다.
"""
```

## 3. Python 클래스·함수 템플릿

PEP 257을 따르고 **Google 스타일 Docstring**을 사용한다. 클래스는 책임·주요 상태·생명주기를, 함수는 목적·인자·반환·예외·부작용을 설명한다.

```python
def decide_next_step(result: VerificationResult, revision_count: int) -> str:
    """검증 결과를 바탕으로 Supervisor의 다음 단계를 결정한다.

    Args:
        result: 근거 검증 결과. PASS, REVISE, INSUFFICIENT 중 하나다.
        revision_count: 이미 수행한 재검토 횟수.

    Returns:
        finalize, revise 또는 insufficient.

    Raises:
        ValueError: 지원하지 않는 검증 상태를 받은 경우.

    Notes:
        무한 루프를 방지하기 위해 재검토를 한 번으로 제한한다.
    """
    # 근거 검증을 통과한 답변만 바로 확정한다.
    if result.status == "PASS":
        return "finalize"

    # 첫 번째 수정 요청에만 재검토 기회를 부여한다.
    if result.status == "REVISE":
        return "revise" if revision_count < 1 else "insufficient"

    # 근거가 부족한 답변은 성공으로 포장하지 않는다.
    if result.status == "INSUFFICIENT":
        return "insufficient"

    # 알 수 없는 상태를 조용히 통과시키면 검증 우회가 발생할 수 있다.
    raise ValueError(f"지원하지 않는 검증 상태: {result.status}")
```

> 예시는 주석 형식 설명용이다. 실제 코드에서는 사용 중인 타입·상태 정의에 맞춰 작성한다.

## 4. 분기·알고리즘·예외 설명

다음 지점에는 인라인 주석 또는 짧은 블록 주석을 둔다.

- `if/elif/else`, `match`, 조건부 LangGraph Edge의 **판단 기준과 이유**
- 검색 결과 없음, API 실패, LLM 타임아웃, 재시도, Fallback, 조기 종료
- 비동기 실행, 스레드 Context 전파, 동시성·상태 전이, 캐시·영속화
- RAG의 검색 대상·컬렉션 선택·필터·출처 메타데이터·근거 부족 처리
- 개인정보 마스킹, 인증, 데이터 저장·삭제처럼 실패 비용이 높은 처리

조건이 자명한 단순 분기는 주석을 강제하지 않는다. 중요한 분기에는 **조건 / 선택 결과 / 그렇게 설계한 이유**가 드러나야 한다.

## 5. LangGraph·Agent 전용 규칙

각 Node에는 다음을 기록한다.

1. Node의 역할과 호출 시점
2. 입력 State에서 읽는 필드
3. 변경·추가하는 State 필드
4. 호출하는 Agent·Tool·외부 의존성
5. 다음 Node로 이동하는 조건
6. 예외, 재시도, 종료 및 근거 부족 처리

복잡한 Workflow 파일의 모듈 Docstring에는 텍스트 흐름도를 넣는다. `PASS`, `REVISE`, `INSUFFICIENT`의 의미와 최대 재검토 횟수를 코드 근처에서 설명한다.

## 6. 법률 분석·RAG 전용 규칙

- 검색 대상과 컬렉션 선택 근거, 임베딩 모델 호환성, 검색 파라미터의 의미를 설명한다.
- 검색 결과가 없을 때와 검색 시스템 오류를 구분해 설명한다.
- 주장 → 검색 문서 → 출처 ID 연결 및 검증 한계를 명시한다.
- **제품 내부 정책**과 **실제 법률 규정**을 혼동하지 않는다. 법령·판례 관련 주석에는 확인 가능한 출처가 있을 때만 이를 표기한다.
- LLM이 추론한 사실을 확인된 사실로 기록하지 않는다.

## 7. TypeScript·React 템플릿

주요 컴포넌트, Hook, API 클라이언트 및 비동기 상태 처리에는 TSDoc/JSDoc을 사용한다.

```typescript
/**
 * 법률 상담 요청과 결과 조회를 관리하는 Hook.
 *
 * 처리 흐름:
 * 1. 상담 요청을 API에 제출하고 requestId를 보관한다.
 * 2. 실행 중에는 상태를 주기적으로 조회한다.
 * 3. 완료 시 답변·출처·검증 상태를 화면에 전달한다.
 *
 * 주의사항:
 * - 컴포넌트 해제 시 폴링을 중지한다.
 * - 네트워크 오류와 법률 근거 부족 상태를 구분한다.
 */
```

복잡한 조건부 렌더링, `useEffect` 의존성, 요청 취소·중복 요청 방지에는 의도를 설명한다. Props·반환 타입은 TypeScript 타입 선언과 주석이 모순되지 않아야 한다.

## 8. 주석 품질 금지 사례

- `# 변수에 값을 넣는다`처럼 코드 그대로 읽는 주석
- 구현되지 않은 기능을 이미 완료한 것처럼 설명하는 주석
- 함수 시그니처나 실제 분기와 다른 오래된 주석
- `TODO`만 적고 원인·후속 조치가 없는 주석
- 민감정보, 실제 사건 당사자의 개인정보를 포함한 예시
- 코드와 무관한 장황한 배경 설명으로 핵심을 가리는 주석

TODO는 `TODO(사유): 필요한 조치 / 관련 이슈 또는 문서` 형태로 작성한다.
