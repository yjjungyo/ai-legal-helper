## 1. 제품 수준의 설계 원칙

1. **특정 시나리오 하드코딩 금지**: SC-012 문자열, 법률 결론 단어 또는 특정 판례번호를 통해 답을 강제하지 않는다. 여러 법 분야에 적용 가능한 범용 법률 쟁점·출처·요건 포섭 계약을 사용한다.
2. **사건 사실과 법률 근거를 구분**: 사용자가 주장한 내용, 승인된 사건 증거, 법령·부칙, 판례를 서로 다른 출처 유형으로 유지한다. 사건명·골드셋 정답·평가 기대내용은 검색 근거가 될 수 없다.
3. **시점 무결성**: n차 상담은 그 시점까지 제출·승인된 증거, 사실, 상담 맥락만 읽는다. 추후 등록된 자료가 이전 상담 재현에 개입해서는 안 된다.
4. **검증 우회 금지**: 법률상 핵심 결론의 출처가 없으면 다른 형식적 조건이 PASS라도 정답으로 통과시키지 않는다. 부분 보존은 *주장별 출처 검증*을 전제로 한다.
5. **책임 추적 가능성**: 입력 증거 스냅샷(원본 해시·문서 ID), 검색된 출처, 법률요건 적용, 검증 상태, 최종 사용자 응답을 별도 관측하고 추적한다.
6. **성능은 정확성 뒤**: 검색이 실패한 상태에서 근거 없이 반복되는 LLM 재작성을 중단하되, 실제 새로운 근거 확보·법리 변경 시 필요한 검증까지 생략해서는 안 된다.
7. **최소 영향 변경·검증 순서 준수**: 단계별 소스/영향 분석 → 수정 → 단위·회귀 검증 → 사용자 확인. 기존 전체 E2E 기본 경로와 KPI/체크포인트는 수동 재현 작업으로 오염시키지 않는다.
8. **Gemini와의 협업**: 각 함수 주석에는 불변식(invariant), 의도(why), 실패 조건, 다른 경로와의 관계를 기록한다. 근거 없는 '완료/통과' 문구를 쓰지 않는다.

## 2. 원본 SC-012 재현 사실

질문: 공동상속인 3명, 상속재산분할 소송 진행 중, 임차인이 각 상속인에게 반환채무 전액을 청구할 수 있는가.

- 실패 Trace: `artifacts/langfuse_review/trace_330c30e9-6a30-4fc3-8201-72302620a8ac.json`
- trace 실행 commit: `f3224961ff5bcb731018a6adc11773910f5cb729`; 대상 main과 차이 있음
- 반환: `INSUFFICIENT / WITHHELD`, 335.51초, 196,311 토큰, 12 LLM 호출
- 5회 verification 누적 시간: 약 246.69초(전체의 약 73.5%)
- Issue Planner: 질문의 '상속재산분할'을 임대인 분할변제 제안으로 오인하여 `ISSUE_INSTALLMENT_PROPOSAL` 생성

- 같은 Trace의 평가용 `consultation_context.answer`(228자)와 `finalize_node.output.answer`(263자)가 서로 다르다. Presentation 후처리일 가능성이 있으므로 답변을 덮어쓰지 말고 계층별 출력과 해시를 보존해야 한다.

## 3. 6단계 개발 순서와 변경 계약

### 1단계 — 재테스트 격리 및 Trace 계층 구분 (이번 브랜치 구현 대상)

**목표:** SC-012의 2차 질문을 반드시 신규 사건에서 1차→2차 순서로 실행하고, E03/E04 이후 등록되는 3차 증거(E05~E07)를 원천 차단. 대화 맥락과 증거 누적을 유지한 상태의 복제 가능한 재현.

**설계**
- 기존 `run_complex_10cases_e2ev6_hitl_auto.py`의 `run_case_evaluation`에 선택적 `stop_after_turn` 인자를 추가하여 공통 실행 경로를 재사용한다.
- `scripts/evaluation/replay_case_turn_v6.py`는 단일 사건 지정, `--through-turn N` 옵션으로 새 Case ID 및 conversation ID를 생성하고 필요한 이전 턴부터 순차 실행한다.
- 재현 모드가 기존 `scratch/e2e_complex10_results_v6.json`, 기존 KPI 파일, 기존 Trace Catalog, 기존 보고서를 덮어쓰지 않도록 일반 E2E의 완료/리포팅 단계 전에 반환한다. 재현 전용 결과 JSON에 새로운 DB 사건 ID와 전체 실행 결과를 기록한다.
- 각 상담 직전 DB에 존재하는 해당 사건 EvidenceDocument의 실제 파일명 집합과 **1차~현재 차수** 증거 디렉터리의 파일명 집합을 비교한다. 다른 문서나 중복 이름이 있으면 **상담 시작 전 예외 발생**. 검증 대상은 등록 상태가 아닌 DB 실제 행이며, 새 사건에는 이전 실행 결과가 없어야 한다.
- 증거 스냅샷에 사건 ID, 턴 번호, 문서 ID, 원본 이름, sha256, 승인 상태를 수집해 Trace와 재현 결과에 남긴다. 예상/실제 증거 집합 일치로만 PASS를 부여하며, AI 답변 정확도의 PASS와 혼동하지 않는다.
- `export_trace_json`은 평가용 실제 API 답변과 Langfuse `finalize_node` 출력의 SHA256 및 비교 결과를 **프로비넌스**로 추가한다. 둘을 자동 교체하거나 오류로 강제하지 않는다. Langfuse 응답이 없을 때 `UNAVAILABLE`로 표시하여 거짓 일치를 방지한다.
- 이 실행에서는 3차 증거·대응계획·법률문서 생성을 수행하지 않는다. 기본 10건 E2E 호출의 동작은 그대로 유지한다.

**수용 조건**
1. 새 사건이 생성된다(이전 `acdb832e-449e-4858-9346-650e9097ed10` ID 재사용 금지).
2. SC-012 2차 직전 DB의 문서 이름 집합은 E01~E04이고 E05~E07이 없다.
3. 1차와 2차 모두 같은 새 사건 ID와 대화 ID로 실행한다.
4. 기존 V6 체크포인트/KPI/카탈로그/보고서는 수정되지 않는다.
5. JSON의 `answer_provenance`에 실제 사용자 반환문/최종 노드 동일 여부, 원문 길이와 해시, 추적 불가 사유를 기록한다.
6. 테스트는 실제 실행 전에 소스 수준 단위테스트 및 가능 범위의 회귀테스트 수행; 실제 LLM+DB 통합은 사용자가 직접 검증한다.

### 2단계 — 범용 법률 쟁점 계획 (1단계 사용자 확인 후)

- `resolved_query`의 의미적 법률 쟁점을 구조화하되, 질문 원문을 최우선 기준으로 유지한다. 판단 쟁점 / 필수 사실 / 필요 근거(법령·판례) / 미확인사항 출력.
- `상속재산분할` 같은 특정 키워드 예외나 `ISSUE_CO_HEIR_LEASE_SUCCESSION`만의 하드코딩은 금지. 기존 분할변제 케이스 회귀 보장.
- RAG 검색 쿼리에서 사례명 및 평가 정답에 해당할 수 있는 메타데이터를 제외한다. 법률 쟁점과 날짜·순위 등 중요한 사건 사실을 연결한다.

### 3단계 — 판례·법령 복합 검색 (1단계 사용자 확인 후)

- `legal_search_requests`에 출처 유형(`STATUTE/PRECEDENT/BOTH`)을 명시. 검증기가 '판례 필요'라고 했는데 법령만 검색하는 불일치 방지.
- 국가법령정보 판례 검색+원문 API, 오류·빈 결과·재시도·쿼리 로그·중복 제거·인용 ID·출처 검증을 구현.
- `PRECEDENT` 타입은 현재 source schema 재사용, 법령 시점·부칙 로직과 혼동 금지.

### 4단계 — 법률요건 포섭 (1단계 사용자 확인 후)

- 인용 판례의 당사자·사실·법률쟁점·판시 요건과 사건의 승인 사실을 비교한다. 유사 키워드만으로 법리를 적용하지 않는다.
- 공동상속인 내부 구상·채무의 대외적 성질·임대차 종료 및 이행기 등은 다른 판단 요소로 다룬다.
- 검증기는 요건별 적용, 반대 근거와 시점의 논리일관성을 검사한다.

### 5단계 — 검증·부분 보존·비용 최적화 (1단계 사용자 확인 후)

- 신규 근거가 없이 동일한 핵심 누락으로 반복 재작성하는 루프 중단. 새로운 증거·법리·실질 텍스트 패치에 따른 검증 재실행은 유지.
- `CAUTIONARY`가 미검증 핵심 법리 통과 수단이 되지 않도록 주장별 출처와 유효성 PASS만 전달한다.
- 법적 근거가 부족하면 해당 결론을 보류하고 확인된 주변 정보만 분리해 설명한다.

### 6단계 — 회귀·성능·감사보고 (1단계 사용자 확인 후)

- SC-011~020, 정상 분할변제, 상속, 경매 선후순위, 법령 시행일/부칙, 허위 판례 입력 및 판례 API 장애.
- 지표: 정답률/보류 정확도, 인용 근거 무결성, Trace 응답 일치(변환 구분), 턴별 증거 격리, 토큰/호출/지연.
- 실제 지표는 통합 테스트 후 기입. 미실행 항목을 PASS로 기록 금지.

## 4. 변경 범위 관리

- 1단계는 생산 워크플로우 / Issue Planner / Verifier / 재무 KPI의 법률 판단 로직을 수정하지 않는다.
- 기본 E2E 10사건 실행의 인수 및 결과 파일 호환을 유지한다.
- 새 재현 러너는 1~N 턴을 **신규 사건**으로 실행하며 체크포인트의 '기완료 건 스킵' 규칙에 종속되지 않는다.
- 실제 수동 테스트에서 Trace 속 추가 증거가 여전히 발견되면 생산 검색 경로에서 case_id 필터를 별도로 추적한다. 이를 단순한 테스트 재사용 문제로 무조건 간주하지 않는다.
