# SC-012 범용 Issue Planner 개선 설계서 / Gemini 인계 문서

- 기준: `main@f8f497477dedf605dff5e13d3b16eb4a9f7dd6f0`
- 작업 브랜치: `fix/semantic-issue-planner-sc012-20261115`
- 범위: **2번 범용 Issue Planner 개선만 구현**. 증거 격리·Trace 정합성(1번), 판례 API(3번), 법률요건 포섭(4번), 검증 루프(5번)는 이번 단계의 기능 변경에서 제외한다.
- 의사결정: **신규 LLM 호출이나 LangGraph 노드를 추가하지 않고**, 기존 후속 상담의 `analyze_consultation_intent` 호출에서 *법률 쟁점 윤곽*을 함께 추출한다. 신규 턴과 LLM 응답 불완전 시에는 질문을 보존하는 결정론적 폴백을 둔다.

## 1. 결함과 소스 근거

1. `workflows/issue_planner.py`의 키워드 `분할`은 분할변제·상속재산분할 등의 법률개념을 구분하지 못한다. `보증금` 같은 다른 문장의 용어와도 교차 매칭한다.
2. `ISSUE_LEASE_TERMINATION`은 `반환` 단어만 있어도 자동 부착한다. 특정 채무의 *이행 책임 주체*를 묻는 질문에도 계약 해지 및 만료를 먼저 검사해 검색을 오염시킨다.
3. `legal_workflow.py::run_agents_node`는 `case_evidence_briefing.title`을 검색에 그대로 포함한다. SC-012 테스트 제목에는 `불가분채무`라는 기대 결론이 포함되어 데이터 누출 및 편향 위험이 있다.
4. 후속 상담에서는 이미 Intent Analyzer LLM이 `resolved_query`를 만든다. 하지만 그 의미 판단은 규칙식 Issue Planner로 전달되지 않아, 사용자 질문의 대상과 쟁점 분해가 서로 어긋난다.

## 2. 설계 원칙

- **쿼리 충실성**: 사용자 원문 질문이 해석의 최우선 자료. 문맥 복원 질의는 보조. 기존 답변이나 사건 제목은 정답/법적 사실로 승격하지 않는다.
- **법률 분야 비종속**: 상속법/임대차/노동법 별 `if`를 무한 확장하지 않는다. 중립적인 사실·권리·의무·쟁점·확인할 조문 후보 필드로 표현한다.
- **추론과 검증 분리**: Intent Analyzer가 제안한 법령/요건은 *후보*이며 진위가 확인된 출처가 아니다. 판례번호·결론을 생성해서 통과시키지 않는다.
- **재사용**: 기존 `IntentDecision` 구조와 `LegalIssueTask` JSON contract 사용. 병렬 새로운 LLM 호출 금지, 총 호출 수 증가 최소화.
- **보수적 폴백**: 구조화 쟁점이 비어 있거나 LLM 응답이 구형이면 핵심 원문 질문을 반드시 하나의 Issue로 남긴다. 비관련 레거시 Issue를 무작정 최상단 검색에 추가하지 않는다.
- **판정 중립성**: 쟁점은 `~인지`, `~여부`처럼 답을 결정하지 않는 질문이어야 한다. '선순위 임차인', '불가분채무로 확정', '상속인 누구에게나 전액 가능' 등 결론을 미리 단정 금지.
- **검색 입력 건전성**: 사건 제목·테스트 시나리오명·예상 정답을 벡터 검색어로 쓰지 않는다. 질문의 핵심 법률 요건과 사건에서 확인된 사실만 쿼리 구성에 사용한다.
- **검증과 관측**: 계획 결과를 Issue ID / 법률 질문 / 필수 사실 / 후보 법령/출처 형태로 남기고, 단계별 회귀테스트에서 정상/오탐/빈 LLM/비관련 주제 확인.

## 3. 구현 계약

### Intent Analyzer (`agents/intent_analyzer.py`)

- 출력 JSON의 선택적 `legal_issue_outlines`: 복합 질문의 핵심 쟁점 최대 4개, 각 `question`, `required_fact_keys`, `candidate_statutes`를 반환.
- LLM 파싱 시 배열/문자열/크기를 강제하고 비정상 데이터는 무시. 이전 JSON 출력과 호환되게 기본 `[]`.
- 후보 조문은 법령 조회 전까진 `candidate`이며 관련성이 없거나 불확실하면 빈 리스트 허용.
- 이번 기능을 위해 추가 LLM 호출하지 않는다.

### Issue Planner (`workflows/issue_planner.py`)

- `plan_legal_issues`에 후속 상담에 대한 선택적 구조화 쟁점 전달.
- **유효한 의미 윤곽이 있으면 그것을 우선적으로 LegalIssueTask로 변환**하며, 필요한 Fact/Evidence label을 기존 `_match_facts_and_evidences`로 매핑.
- 후속 원문 질문이 명확한데 윤곽이 없으면 **질문 그대로의 우선 Issue**를 반환하여 검색의 기준을 보호한다. 후속 질문에서 이미 결정된 기존 범용 쟁점들이 임의의 추가 쟁점이 되는 것보다 원문을 우선한다.
- 특정 분야 규칙 또는 정규식 예외는 추가하지 않는다. 기존 `plan_legal_issues(question, briefing)`의 호출은 역호환 보존.
- 가짜 증거 참조 식별 등 안전 검사는 의미 윤곽 경로에서도 잃지 않는다.
- 생성된 `required_statutes`는 확보·검증되지 않은 후보를 요구사항으로 간주하는 현재 downstream 계약 특성상, 명시적으로 알려진 조문만 유효 형식일 때만 사용; 나머지는 `candidate_statutes`에 둔다. **인용 결론은 별도 검증 필수**.

### Workflow (`workflows/legal_workflow.py`)

- Supervisor에서 이미 구한 IntentDecision의 `legal_issue_outlines`을 Issue Planner로 전달. 첫 턴에는 기존 동작을 보존.
- RAG 쿼리에서 사건 제목 삭제; 문제 해결에 필요한 원문/복원 질의 및 최대 3개의 중립적 쟁점 질문만 포함.
- 우선순위가 높은 현재 질문 쟁점이 검색 첫 번째에 와야 한다.
- LLM이 기존 사건명이나 과거 AI 답변의 법률 결론을 무단으로 확정하지 않도록 프롬프트 명시.

## 4. 검증 계획

1. **SC-012 멀티턴**: '상속재산분할'이 '임대인의 분할변제 제안'으로 바뀌지 않고, 공동상속인의 반환채무 책임을 질문 그대로 보존.
2. **정상 분할제안**: '30% 먼저 돌려주고 잔액을 1년 뒤 지급' 등의 명시적 제안이면 분할제안 Issue를 유지.
3. **SC-013 경매**: 근저당 설정, 전입·확정일자 선후와 낙찰자 대항을 중립적으로 질문; 사전 결론 금지.
4. **비임대차 법률**: 임금체불, 노동계약 해고 등도 동일 구조로 Issue 생성.
5. **하위 호환**: `LegalIssueTask` 및 `IntentDecision` 기존 테스트. LLM 응답에 신필드 없거나 잘못된 경우 런타임 크래시 없이 폴백.
6. **쿼리 누출 방지**: `run_agents_node`가 케이스명/테스트셋 정답을 벡터 검색어로 합성하지 않음.
7. **추가 LLM 호출 없음**: 후속 상담 기존 1회 분석에 필드를 추가할 뿐. 실제 엔드투엔드 품질/지연은 사용자 테스트에서 확정.

## 5. 수용과 한계

이번 단계에서 Issue 구조화와 검색 쿼리 범위는 개선하지만 **판례를 실제로 찾아오는 검색 엔진은 별도 3단계**이며, SC-012의 최종 정답을 이 수정만으로 보장하지 않는다.

후속 Gemini 작업 시: 실제 브랜치의 최신 코드와 이 문서의 계약을 먼저 읽고, 새 프롬프트 필드의 파싱/호환/일반 사건 영향도를 반드시 확인할 것. 법률 정답을 키워드로 강제하는 패치를 제안하지 말 것.
