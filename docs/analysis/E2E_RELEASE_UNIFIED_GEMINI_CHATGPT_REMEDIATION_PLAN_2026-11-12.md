### 절대 지켜야 할 고객가치

> 법을 단순 검색하는 AI가 아니라, **일반 사용자의 사건을 지속적으로 이해하며 증거 수집 → 사실 확정·변경 → 상담 → 대응계획 → 문서까지 지원하는 사건 중심 법률 AI**.

1. **사건의 연속성:** 동일 사건에서 추가된 증거·변경된 사실이 후속 상담에 반영된다. 대화 원문을 줄이는 것은 사건 기억을 지우는 것이 아니다.
2. **근거의 추적성:** 실제 증거 파일명·원문 span·승인 상태·법령 조문/시행본/부칙·인용 연결을 보존한다. 승인되지 않은 주장을 확정 사실로 바꾸지 않는다.
3. **법률 정확도:** 적용 법령의 사건일·행위·부칙을 의미적으로 판단한다. Python 정규식으로 법률 적용 여부를 최종 판정하지 않는다.
4. **사용자 이해:** 핵심 결론 → 지금 해야 할 일 → 상세 분석 → 증거·법령 근거 → 추가 확인사항. 불확실성, 조건, 예외, 미확인 사실을 숨기지 않는다.
5. **안전한 실행:** HITL 승인, 장시간 상담 진행상태, 중단/재개, 답변 검증, 근거 변경 시 재상담 표시를 유지한다.
6. **확장성:** 임대차는 MVP 우선 도메인이다. 타 법률 분야를 허위로 지원한다고 주장하지 않으며 범용 기능과 도메인 규칙을 분리한다.

## 2. Gemini Codebase Audit의 8개 과제 전수 재검토

### G-01 진행 단계 프로토콜 불일치 — **채택·수정 / 출시 전 필수**

**Gemini 원안:** 백엔드 `step_1..step_6`과 프론트 `INTENT_ANALYSIS..FINAL_SYNTHESIS` 불일치, `STATUTE_APPROVAL` 비교 실패. 프론트 식별자를 서버에 맞추고 노드 시작 이벤트를 추가.

**ChatGPT 소스 재검토:** `frontend/src/components/chat/ConsultationProgress.tsx` 32~39행의 `DEFAULT_STEPS`, 90~99행의 `STATUTE_APPROVAL` 비교가 실제 존재. 서버 진행 식별자와 계약 불일치 위험은 실재. 단, 승인 대기가 항상 'step_3'인지는 **상태 매핑과 실행 경로를 확인해야 하므로** 단순 문자열 치환만으로 완료 선언 금지. `astream(stream_mode="updates")`의 완료 중심 이벤트로 긴 노드 실행 중 표시가 지연될 수 있음.

**통합안:** 서버를 진행상태 SSOT로 정하고 `progress_step_id`, `phase`, `status`, `updated_at`, `approval_request_id`의 명시적 API 계약을 정의. 프론트 초기값도 동일 ID 사용. `APPROVAL_REQUIRED`는 특정 단계 번호에 하드코딩하지 않고 서버 제공 `phase=STATUTE_APPROVAL` 또는 `approval_request`로 연결. 노드 진입 RUNNING, 완료 COMPLETED, 실패 FAILED, HITL WAITING_APPROVAL 이벤트를 보장하고 기존 클라이언트 호환성 검토.

**Gemini 작업 지시:** 스키마→라우트→프론트 3개 파일의 상태 ID 매핑표 작성; API 단위 테스트와 브라우저 폴링/승인/거절/재개 통합 테스트. 서버가 진행 이벤트를 보낼 수 없는 구간은 마지막 업데이트 시간 표시; 가짜 진행률·가짜 완료 단계 금지.

**완료 기준:** 최초 폴링 깜빡임 없음, 승인 요청 시 정확한 단계 대기, 승인·거절·실패·재개 일관성, 장시간 실행 중 RUNNING 유지. **우선순위 S3**.

### G-02 로컬 법령 사전 적재 vs NEED_MORE_LAW — **조건부 채택 / 정확도 선행**

**Gemini 원안:** 이미 로컬 조문이 있으면 `READY`를 유도해 HITL/재분석 감소.

**ChatGPT 소스 재검토:** `document_answer.py` 273~295행에 `NEED_MORE_LAW` 규약이 있고 추가 검색 분기가 존재. 그러나 **'로컬에 조문 있음'과 '법적으로 충분함'은 다르다**. 해당 조문이 시행 전/후 버전인지, 부칙 적용례가 있는지, 핵심 질문의 법적 요건이 충족되는지 확인해야 한다. SC001-1의 241초 원인을 단일 프롬프트 규약만으로 확정할 trace 증거는 본 재검토에서 확보하지 못했다.

**통합안:** `required_statutes`와 `available_statutes`의 **조문·법령 ID·시행일·버전·부칙·쟁점 충족도**를 비교하는 `LegalSourceCoverage`를 작성. 모델은 `missing_laws`에 법령명만 아니라 부족한 **조문/버전/적용례/근거 이유**를 제시. 서버는 '존재 여부'가 아닌 **누락 근거의 타당성**을 검토해 필요할 때만 공식 검색. 불충분하거나 법령 버전 충돌 시 READY 강제 금지. 기존 HITL 승인·재개 유지.

**Gemini 작업 지시:** SC001-1 Langfuse trace에서 실제 missing_laws, 로컬 source_id, 호출 시간 확인 → coverage manifest 구현 → 법령 버전/부칙 충분성 단위 테스트 → 재실행. HITL 생략 조건을 로그로 설명 가능하게 만들 것.

**완료 기준:** 충분한 출처에 대한 중복 검색 감소; 불충분한 부칙/시행본에서 검색 유지; 환각 법령 인용 0건. **S2**, 단 **C-01/C-02/C-04 선행**.

### G-03 임대차 키워드 중심 issue_planner — **문제 인식 채택, 출시 전 대규모 일반화 보류**

**Gemini 원안:** 키워드 규칙 때문에 타 도메인이 `ISSUE_GENERAL_ANALYSIS`로 수렴, 도메인별 템플릿 일반화.

**ChatGPT 소스 재검토:** `issue_planner.py`는 실제로 693행이고 `plan_legal_issues` 및 `ISSUE_GENERAL_ANALYSIS` fallback 존재. 그러나 파일 주석은 임대차·근로·채권 도메인 일반화를 언급한다. **'전적으로 임대차 정규식만 사용' 또는 '모든 타 도메인이 무조건 실패'는 경로별 실행 테스트 없이 단정 불가.** 법률 도메인 분류와 검색의 범용성은 분리해야 한다.

**통합안:** 이번 릴리스에서는 임대차 경로의 정확도와 범용 질문의 **지원범위 고지/안전한 fallback** 보장. `domain`, `issue_tasks`, `required_sources`를 인터페이스로 정의하되 노동법 등 새 법률 모듈 구현은 릴리스 후. 특정 평가 시나리오 문구에 맞춘 하드코딩 추가 금지.

**완료 기준:** 임대차 복합 쟁점 분리 유지, 미지원/혼합 도메인에서 허위 근거·확정 결론 없음. **S5 / 후속**.

### G-04 화면 답변 중복 표시 — **채택·보완 / 출시 전 필수**

**Gemini 원안:** `builder.py`가 번호형 헤딩을 인식하지 않아 전체 답변을 LEAD로 분류, 프론트 fallback으로 같은 본문 두 번 출력. `^\d+\.\s+...` 추가.

**ChatGPT 소스 재검토:** `builder.py` 22~36행은 Markdown/# 및 대괄호 제목만 인식; `consultationDigest.ts` 124~148행에서 lead 블록 제외; `VerifiedPresentationView.tsx` 72~81행에서 detailedAnswer가 비면 fullAnswer를 렌더링하는 경로 존재. **중복 표시 가능성은 소스상 확인됨.** 하지만 모든 `1. ...`을 헤딩으로 간주하면 일반 행동 목록, 법률 요건 나열, 조문 인용까지 섹션으로 분할할 수 있다.

**통합안:** (1) `1. 핵심 결론`, `2. 지금 해야 할 일` 등 **허용된 섹션 제목**과 Markdown 제목을 인식하되 일반 번호 목록은 본문 유지; (2) lead가 원문 전체와 같거나 상세가 비면 **한 번만 표시**; (3) 원문 보존·SHA/claim citation 매핑 보장; (4) 조건·예외·근거를 미리보기 추출 과정에서 삭제하지 않음.

**Gemini 작업 지시:** 백엔드 섹션 분리 테스트(정식 헤딩/일반 목록/인용/빈 문서), 프론트 렌더 테스트(LEAD 전체/분리/빈 상세/근거 링크), E2E 스크린샷 전후 비교.

**완료 기준:** 결론·상세 중복 0건, 원문 유실 0건, 증거 인용 클릭 정상. **S3**.

**Gemini 원안:** 단순 패스스루 노드를 synthesize로 통합해 체크포인트·트레이스 비용 감소.

### G-07 5,745행 legal_workflow.py 분할 — **원칙 채택, 출시 전 보류**

**Gemini 원안:** Document/Legacy workflow 물리적 분리.

**ChatGPT 소스 재검토:** 최신 파일 5,746행, `build_legal_graph()` 등록 노드는 17개. 분기 혼재는 유지보수 위험이지만 출시 하루 전 대규모 분할은 import, state schema, conditional edge, HITL resume, checkpoint ID에 광범위한 회귀 위험을 만든다.

**통합안:** 이번 릴리스는 **행동 보존형 국소 변경만 허용**. 분리 설계는 출시 후 `context preparation / source coverage / answer generation / verification / presentation` 인터페이스를 먼저 확정하고 작은 PR로 이동. 기존 graph state와 resume compatibility 계획 필수.

### G-08 멀티턴 이력 3중 주입 — **채택하되 Gemini의 'messages SSOT' 수정**

**Gemini 원안:** `case_context`의 이전 턴 제거, `messages`만 SSOT, `user_history` 직전 1턴 유지.

**ChatGPT 소스 재검토:** `legal_workflow.py` 362행 `format_context_for_prompt(max_turns=2)`, 5402행 `to_chat_history_messages(max_turns=3)`, `document_consultation.py`의 user_history 구성이 중첩 가능. **이전 AI 답변을 SSOT로 삼는 것은 잘못**이며, `messages`를 기본으로 유지하면 대형 AI 답변이 다시 토큰을 소비한다. 다만 실제 history 항목이 각 250자로 제한된 경로도 있으므로 전체 75k 토큰의 주범이라고 단정하지 않는다. 원문 증거/법령 및 verification JSON 등도 입력 토큰 구성비 측정 필요.

**통합안:** **사건 DB의 증거·승인 사실·사건 타임라인이 SSOT**. 대화 이력은 `conversation_reference` 별도 계층으로 분리. 기본 질문은 이력 0턴, 후속 질문의 생략 지시어가 감지되면 필요한 과거 사용자 발언/참조 사건만 최소 복원. 이전 AI 답변은 참고용으로만 제한하고 확정 사실로 사용 금지. 사용자 진술과 승인된 증거를 명시적으로 구별. `case_context`에서 과거 문답 제거해도 최신 사실은 유지.

**Gemini 작업 지시:** 먼저 프롬프트별 history / case facts / evidence / statute / output-schema 토큰 계측 → 중복 이력 제거 1개 경로씩 변경 → SC001 3턴 연속, '그럼 이사 전에?', '앞서 말한 날짜' 등 후속 질문 회귀.

**완료 기준:** 지시어 복원 정확도 유지, 사건 신규 증거 반영 유지, 입력 토큰 실측 감소. **S2**.

## 4. ChatGPT P1 최적화 과제와 Gemini 연결

### C-07 검색·재작성·재검증 루프 — **S2**

G-02와 결합. `synthesize → NEED_MORE_LAW → approval → execute → re_analyze → verification → revise → reverify`의 실제 경로를 trace로 확인. **LLM 호출 수 자체보다 필수 검증 누락 없이 중복 호출 제거**가 목적. `LegalSourceCoverage`로 재검색 필요성 설명, 동일 조문/버전 요청 캐시, 수정 사유가 있는 경우만 국소 재작성. 수정이 없으면 같은 입력 재검증 반복 금지. 최대 재시도 횟수와 중단 사유 명시. 판정 불가일 때 PASS 강제 금지.

### C-08 상담 전용 최소 경로 — **S4 / 안전성 검증 후 선택**

G-06/G-07의 구조 변경을 흡수하는 장기 목표: `Context Preparation → Legal Retrieval → Synthesizer → Verification → Finalize`, 조건부 법령 추가 검색·HITL·부분 수정. 기존 일반 대화/문서 생성/증거 등록은 각 책임 유지. **내일까지 그래프 전면 교체하지 않는다.** 우선 현재 그래프에서 불필요한 호출·컨텍스트만 제거.

### C-09 LegalState/체크포인트 경량화 — **S4 / 출시 후 우선**

G-06과 연결. 긴 원문은 source ref+버전+해시로 참조, 사건 사실/승인/질문/검증 결과는 유지. 단, HITL 중단 후 PostgreSQL checkpointer 재개 시 출처 스냅샷이 달라지면 잘못된 답변 가능. `get_checkpointer()`만 보고 전체가 MemorySaver라고 판단하지 말 것: `run_legal_consultation()` 5718~5738행에서 설정에 따라 `AsyncPostgresSaver` 주입. 메모리/DB 양쪽에서 재개 테스트 후 적용.

## 9. 최종 결론

**Gemini 안의 장점:** UI 결함, 진행상태, 불필요한 검색, 대화 이력 중복, 코드 복잡성을 구체적으로 발견.  
**ChatGPT 안의 추가 기여:** 법령 버전·사건일·부칙, 검증 누락 반증, 금액 역할, 승인/EvidenceSpan의 **출시 차단 정확도 위험**을 식별하고 성능 개선의 안전 조건을 제시.  
**통합 결론:** Gemini의 성능·UX 개선을 채택하되 **ChatGPT가 식별한 정확도 P0를 선행 조건**으로 둔다. 마감 전에는 기존 그래프 전면 개편보다 작고 검증 가능한 수정이 안전하다. 최종 목표는 '5턴 평가 PASS'나 '노드 수 감소'가 아니라 **실제 고객의 사건을 지속적으로 이해하고, 근거 있는 법률 결론을 빠르고 합리적 비용으로 제공하는 출시 가능한 E2E 제품**이다.

# 부록 A. 2026-11-12 실측 증거를 반영한 2차 재검토 및 실행 순서 보정 (ChatGPT)

> **본 부록이 본문과 충돌하는 경우 본 부록의 증거 등급·실행 순서·검증 원칙을 우선 적용한다.** 원문 Gemini 보고서와 1차 ChatGPT 보고서는 이력 보존을 위해 수정하지 않는다.

## A1. 중요한 사실관계 정정

사용자가 확인한 Gemini 작업 조건은 다음과 같다.

1. **Gemini는 로컬에서 GitHub와 동일 버전의 소스코드를 확인했다.**
2. **Gemini는 로컬 실행 로그 및 Langfuse trace를 열람하고 Codebase Audit 개선안을 작성했다.**
3. **Gemini는 Langfuse를 확인하여 KPI 자동평가 엑셀을 작성했다.**
4. GitHub의 `05b9e79b40ae8999ec83cd38b0bd0e4b397d76b6` 커밋에서 `docs/evaluation/kpi/AI_Legal_Helper_KPI_202611120608_자동평가_e2ev2.xlsx` 파일이 추가된 사실을 확인했다.

**정정:** 1차 ChatGPT 통합안은 Gemini의 진단을 주로 정적 코드에서 도출된 가설처럼 다루었다. 이는 **증거의 출처와 강도를 과소평가**한 것이다. 특히 SC001~SC003의 소요시간·토큰·호출 수 및 Gemini가 trace로 관찰한 경로는 **Gemini의 실측 기반 분석**으로 명시한다. 다만 ChatGPT는 이번 검토에서 **로컬 Langfuse 원본 trace와 KPI 엑셀의 셀 내용/수식까지 독립 열람·재계산하지 못했다**. 따라서 'Gemini가 실제 확인한 분석'과 'ChatGPT가 별도 재검증한 사실'을 구분한다.

**중요한 추가 근거:** GitHub `05b9e79...` 커밋은 KPI 엑셀만 추가한 것이 아니라 `document_answer.py`, `case_briefing.py`, `grounding_context.py`, `document_consultation.py`, `legal_workflow.py`도 변경했다. 즉 KPI 수치는 특정 **소스 스냅샷 + 평가 데이터 + Langfuse trace**에 묶여 있다. 평가 시점의 SHA와 현재 실행 SHA가 같거나 차이가 문서 커밋뿐인지 확인하여 비교해야 한다.

## A2. 증거 등급 및 판단 기준

| 등급 | 정의 | 이번 자료에 대한 예시 | 허용되는 주장 |
|---|---|---|---|
| **E1: 직접 재현** | 동일 입력/버전으로 실행 및 결과 재확인 | 추후 Gemini가 제공할 재실행 trace + 테스트 | 결함 재현/수정 효과 확정 |
| **E2: 실측 기록** | 로컬 로그·Langfuse·KPI 평가 기록 기반 | Gemini의 E2E V2 감사 및 KPI 엑셀 | 측정된 실행시간/호출/실제 분기 |
| **E3: 소스상 확정** | 정적 코드 분기·구현 확인 | `CONTRACT_SIGNED` 자동 설정, UI ID 불일치 | 해당 위험 경로 존재 |
| **E4: 논리적 위험** | 코드상 가능하나 재현 미확인 | 버전 중복 제거로 실제 잘못된 판정이 발생했는지 | 위험/재현 필요, '실제 장애' 단정 금지 |
| **E5: 예상 효과** | 수정 전후 동일 입력 실측 없음 | '241초→60~80초', '70% 절감' | 목표/가설, 성과 단정 금지 |

**Gemini 실측 분석의 취급:** G-02 불필요 법령 검색, G-08 대화 중복, 5-hop 경로 등은 Gemini가 trace로 확인했다고 명시한 경우 **E2**로 우선 기록한다. ChatGPT는 원본 trace가 없다는 이유만으로 이를 E4로 강등하지 않는다. 단, *정확히 어떤 호출이 얼마를 차지했는지*는 trace ID·observation ID·시각을 연결하여 다시 검토할 수 있어야 한다.

**ChatGPT P0의 취급:** C-01~C-06은 소스상 위험이 크지만 모든 항목이 실제 사용자 오답을 발생시켰다고 입증된 것은 아니다. **출시 차단 위험 후보**로 분류하고 짧은 재현 테스트로 E3/E4를 E1로 올리거나, 재현되지 않으면 보류/완화한다. 무조건 여섯 항목 모두 구조를 갈아엎는 것은 금지한다.

## A3. KPI 자동평가 파일의 사용 원칙

**원본 파일:** `docs/evaluation/kpi/AI_Legal_Helper_KPI_202611120608_자동평가_e2ev2.xlsx` (Gemini 작성, GitHub 커밋 존재 확인).

Gemini 작업자는 다음을 **기존 파일에서 먼저 읽어** 표로 제출한다. 새 평가표를 임의로 만들거나 기존 KPI 점수를 폐기하지 않는다.

### G-02 수정 방침의 핵심

Gemini가 **실제 trace에서 불필요한 HITL을 확인했다면** 이는 가장 유력한 즉시 성능 개선 후보 중 하나다. ChatGPT가 요구하는 버전·부칙 충분성은 Gemini의 분석을 부정하는 것이 아니라 **검색을 생략해도 되는 안전 조건**이다. 따라서 '검색은 항상 해야 한다'와 '로컬 법령이 있으면 검색을 항상 생략한다' 모두 틀린 정책이다.

**권장 순서:** (1) SC001-1 실제 trace에서 이미 있던 조문·missing_laws 확인 → (2) 동일 법령·동일 버전·부칙 포함 여부 검증 → (3) 불필요 요청만 억제 → (4) HITL 실제 필요 사례 회귀 → (5) 같은 입력으로 절감치 측정.

### G-08 수정 방침의 핵심

Gemini가 실제 프롬프트/로그에서 `messages + case_context + user_history` 중복을 확인한 사실은 인정한다. 그러나 **중복이 존재한다**는 사실과 **총 75,002/87,486 토큰 중 얼마를 차지한다**는 수치 주장은 별개다. 사용자 사건 기억은 DB 승인 사실·타임라인·증거에서 유지하고, 대화는 후속 질문의 생략 복원에 필요한 최소 문장만 보존한다.

## A6. 내일 마감용 **보정된 최종 작업 순서**

> 1차 보고서의 'S1 정확도 5개 모두 먼저 구현 → S2 성능'은 모든 위험이 재현된 것처럼 취급할 수 있다. **2차 권고는 '빠른 정확도 재현 + Gemini 실측 병목 수정 + 필수 UX + 최종 회귀'**다. 검증에 실패하지 않은 영역을 무조건 재설계하지 않는다.

|---|---|---|---|---|
| **0** | KPI/Trace 증거 고정 | KPI 엑셀 5행과 실제 trace ID·SHA 연결, 병목 순위표 작성 | 분석 | trace 근거와 평가 행 1:1 |

## A7. Gemini에게 전달할 **실측 우선 작업 지시**

1. **기존 KPI 파일을 먼저 읽는다.** 파일명·시트·5개 턴·Trace ID·평가 기준·수식/자동평가 로직을 확인하고 표로 출력한다. 이미 존재하는 측정 결과를 '미측정'이라고 다시 쓰지 않는다.
2. **Trace별 호출 트리**를 작성한다: `node → LLM generation → prompt input/output tokens → 법령 검색 → HITL wait → revise/reverify → finalize`. 정확한 시각, span ID, 중복 prompt/source ID를 연결한다.
3. **Gemini 감사 보고서의 각 주장을 실측/소스/예상으로 태깅**한다. 실측 원인이라면 해당 Trace ID를 붙이고, 성능 개선 예상치는 목표로 남긴다.
4. **ChatGPT 위험 C-01~C-06을 동일 버전 소스에서 재현 테스트**한다. 재현되지 않은 위험은 출시 차단 결함으로 단정하지 않고 조건과 잔여 위험을 명시한다.
5. **실측 최대 병목 하나만 수정**한다. 기존 정확도 테스트 PASS 후 다음 변경으로 이동한다. 변경 전후 동일 증거·법령·모델·질문으로 비교한다.
6. **고객가치 체크:** 새로운 증거 반영, 이전 상담 연속성, 승인 상태, 실제 파일명/출처, 법령 시행일·부칙, HITL, 조치사항/상세 분석 모두 보존.
7. **결과 제출:** GitHub SHA, KPI 행, Trace ID, 실측값, 테스트, 법률 결론 diff, 악화/미해결 위험, 사용자 승인 요청을 한 카드에 정리한다.

## A8. 2차 최종 판단

**Gemini가 로컬 로그와 Langfuse를 확인한 작업의 증거 가치를 인정한다.** ChatGPT의 정적 검토는 이를 대체하거나 무효화하지 않는다. 역할 분담은 다음이 적절하다.

- **Gemini:** 실제 실행 경로·지연 원인·KPI 산출의 1차 실측 근거, 수정 및 로컬 E2E 재현.
- **ChatGPT:** 실측 분석의 해석·우선순위 교차 검토, 법률 정확도 위험 및 고객가치 보존 조건, 안전한 변경 순서.
- **사용자:** 고객가치/품질 우선순위와 출시 Go/No-Go 최종 결정.

**내일 출시 전략:** '정확도 위험을 모두 전면 개편'도 'Gemini 성능 최적화를 무조건 적용'도 아니다. **이미 확보한 Gemini의 실측을 출발점으로, 재현된 정확도 결함을 우선 국소 수정하고, 가장 큰 실제 병목을 안전하게 줄인 뒤, E2E 전체 회귀로 출시 품질을 입증**한다. KPI 점수와 trace가 정확도/성능을 동시에 뒷받침하지 못하면 성능 수치만으로 출시를 선언하지 않는다.
