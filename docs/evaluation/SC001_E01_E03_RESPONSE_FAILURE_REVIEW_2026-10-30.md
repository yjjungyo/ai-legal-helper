## 1. 결론

단순한 모델 문장 생성 문제가 아니다. 현재 코드는 질문에 있는 ‘입금’을 임대인의 일부 반환 진술로 바꾸고, 계약서의 조건부 의무 조항을 실제 종료 사실로 오인할 수 있다. 최종 답변 조립기는 이를 확정적인 종료·반환 청구 안내로 확대하고, 검증된 쟁점이 없어도 분쟁 대응 행동을 출력한다.

이번 사용자의 요청은 등록 증거에 따른 계약·당사자·지급·권리·추가 확인 사항의 분석이다. 종료와 반환 분쟁이 이미 입증되었다는 전제의 대응 절차 안내로 바꾸면 안 된다. 모델을 교체해도 아래 결정적 분기가 유지되면 같은 유형의 오류가 발생할 수 있다.

## 3. 확인된 결함과 코드 위치

### A. ‘입금 자료 분석’을 ‘일부 반환 진술’로 조작 — 재현됨

- `agents/intent_analyzer.py:183`: 후속 질문 폴백에서 ‘입금’이 첫 번째 키워드 조건과 두 번째 조건을 모두 충족한다. 지급 방향·행위 주체·새 사실 진술 여부를 검사하지 않는다.
- `workflows/final_disposition.py:390`: 현재 질문과 resolved_query를 합친 문자열에서 변제 변동을 감지한다.
- 같은 파일 `:408`: ‘입금’만으로 변제 언급 조건이 성립한다.
- 같은 파일 `:588`: 금액이 없어도 ‘의뢰인의 보증금 일부 입금/변제 진술 접수’를 생성한다.

사용자의 질문을 그대로 넣은 `detect_case_delta()` 호출에서, 이전 대화가 없어도 제공된 답변과 같은 일부 변제 진술·확인 요구가 생성되었다. `USER_ALLEGED`라는 태그는 이 문제를 완화하지 않는다. 사용자가 그런 진술을 하지 않았기 때문이다.

의도 분류 폴백은 이전 대화 없음에서 `NEW_LEGAL_ANALYSIS / requires_retrieval=True`, 이전 대화 있음에서 `FACT_CLARIFICATION / requires_retrieval=False`였다. 실제 서비스가 폴백을 사용했는지와 대화 이력 상태는 현재 트레이스 없이 확정할 수 없다. 반면 delta 오류는 이 분류 경로에 의존하지 않고 재현되었다.

### B. 일반 계약 조항을 실제 종료 사건으로 오인 — 재현됨, 최우선

- `case_intelligence/settlement_calculator.py:528`: 묵시적 갱신 여부를 기본 False로 둔다.
- 같은 파일 `:542`: 특정 갱신 문구가 있어야 True가 된다. 갱신 정보 부재를 비갱신으로 취급할 위험이 있다.
- `agents/issue_verifier.py:433`: 약정 만기 경과를 종료 판단 근거로 사용한다.
- 같은 파일 `:437`: 엄격 검증 Fact에 ‘만료’ 또는 ‘종료’가 있기만 해도 종료 조건을 충족시킬 수 있다.
- 같은 파일 `:446`: 계약과 해당 조건 및 법령 출처가 있으면 종료 쟁점을 `VERIFIED`로 판정한다.

E01의 실제 제4조는 다음과 같은 조건부 의무 조항이다.

> 제4조 계약 종료 시 임차인은 목적물을 반환하고 임대인은 보증금을 반환한다.

이 조항을 `EVIDENCE_SUPPORTED` Fact 하나로 넣고 통지·도달·실제 종료 사실을 전혀 넣지 않은 상태에서도, 메모리 내 법령 출처 fixture를 제공하면 `verify_issue()`가 `VERIFIED / TERMINATION_FACTS_AND_LAW_SUPPORTED`를 반환했다.

문서가 이 조항의 존재를 뒷받침한다는 것과 계약이 실제로 끝났다는 것은 서로 다른 명제다. 문서 내용에 대한 Fact 신뢰도 필터만으로 이 구분을 해결할 수 없다.

주택임대차보호법 제6조는 통지 여부 등에 따른 갱신을 규정하므로, 최초 약정 만기일이 지났다는 사실만으로 현재 종료를 확정해서는 안 된다. 실제 갱신·통지·합의·도달 경위를 추가 확인해야 한다. [국가법령정보센터 제6조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1018577289)

### C. 최종 조립기가 검증 이후 새 주장을 생성 — 재현됨

- `workflows/final_disposition.py:804`: 종료 쟁점이 VERIFIED인지 하나의 불리언으로 축약한다.
- 같은 파일 `:833`: VERIFIED이면 실제 종료 근거와 관계없이 ‘기간 만료로 이미 종료 확정’, 반환 채무 이행기 도달, 다음 세입자 사정, 즉시 절차 착수 문장을 생성한다.
- `workflows/legal_workflow.py:1120`: 검증된 초안 뒤에서 `assemble_grounded_answer()`로 최종 문장을 재조립한다.
- 같은 파일 `:1138`: 이후 인용 감사를 하지만 새 문장 전체에 대한 법률 요건 재검증과 동일한 검사는 아니다.

B의 재현 결과를 조립기에 전달하면 사용자 답변과 같은 ‘기간 만료로 이미 종료 확정’ 핵심 결론이 출력되었다. 다음 세입자 관련 사실은 이 입력에 없는데도 생성되었다. 설령 묵시적 갱신 후 적법 해지로 종료가 검증된 다른 사례라도 이 템플릿은 종료 원인을 ‘기간 만료’로 바꿀 수 있다.

### D. 검증된 쟁점 0건이어도 반환 분쟁 조치를 고정 출력 — 재현됨

- `workflows/final_disposition.py:893~938`: 점유 유지, 내용증명·지연손해금, 임차권등기, 소송 등의 행동 목록을 조립한다. 일부 분기는 있지만 기본 반환 분쟁 안내에는 필수 사실별 실행 게이트가 없다.
- 같은 파일 `:901`: 민법 연 5%·소촉법 연 12% 문구를 고정 출력한다. 이행기·이행제공·지체·소송 진행 단계와 관계없이 현재 적용 가능한 것처럼 제시해서는 안 된다.

`assemble_grounded_answer(issue_results=[], ...)`에서도 위 조치들이 출력되었다. 본문에 ‘현재 확정할 수 있는 쟁점이 없다’고 하면서 실행 조치는 확정적으로 제공할 수 있는 구조다.

임차권등기에 따른 권리 보전도 기존 취득 여부와 등기 완료 등 조건을 확인해야 한다. ‘신청’과 ‘등기 완료’를 구분하는 규정이 있는 만큼, 출처 문서의 존재만으로 현재 신청 요건이나 권리 유지 여부를 확정할 수 없다. [국가법령정보센터 제3조의3 제5항](https://law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1018577181)

### E. 증거 공백 목록이 비었다고 증거가 충분하다고 판단 — 재현됨

`workflows/final_disposition.py:958~963`은 `briefing.evidence_gaps`가 비어 있으면 ‘기본 요건사실은 충실히 구비’라고 출력한다. 공백 탐지 미실행·추출 실패·필수 항목 미정의와, 공백이 실제로 없음을 구분하지 않는다. E03의 원본 확인 필요 문구조차 최종 추가 확인 사항에서 누락될 수 있다.

### F. 사실 선별이 질문보다 이미 작성된 초안에 끌림 — 코드 확인

`workflows/final_disposition.py:861`은 핵심 사실 선택에 사용자 질문 대신 `draft_answer`를 전달하고 최대 5개로 제한한다. `score_fact_legal_importance()`는 보증금·반환·종료 같은 키워드를 가중한다.

따라서 잘못된 분쟁 초안과 일반 계약 조항이 실제 당사자·기간·지급 방향보다 우선 노출될 수 있다. 사용자가 요청한 필수 항목별 커버리지를 보장하지 않는다. 단순히 상위 사실 개수를 늘리는 것으로 해결할 문제가 아니다.

### G. `(TXT)`만 보이는 출처 — 원인 미확정

사용자 제공 답변에서 참조 사건 증거는 `(TXT)`만 보이지만 하단 출처에는 파일명이 남아 있다. 현재 백엔드 조립기는 `final_disposition.py:1041~1048`에서 `[파일명] (TXT)`를 생성하며 격리 실행에서도 파일명은 남았다.

따라서 실제 API 응답, 저장된 answer, 프런트 렌더링, 복사된 텍스트를 대조해야 한다. 현재 자료만으로 백엔드 파일명 누락 또는 프런트 버튼 복사 문제 중 하나로 단정하지 않는다. `LegalAnswerView.tsx:95`의 인라인 인용 렌더러와 claim citation 연결을 점검 대상으로 둔다.

추가 위험으로 `LegalAnswerView.tsx:152,162`의 파일명 부분 일치 비교는 빈 문자열에도 참이 될 수 있다. 실제 오연결은 아직 재현하지 않았으며, 빈 이름과 유사 파일명에 대한 회귀 시험이 필요하다.

기존 테스트 실행 명령:

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
backend/.venv/Scripts/python.exe -m pytest backend/tests/unit/test_case_independence_counterexamples.py -k 'distinguish_expiry_from_implicit_renewal or conditional_verifier_leads_to_conditional_disposition' -q -p no:cacheprovider
```

격리 재현은 제품 함수를 직접 호출했고, 증거 ID·Fact·법령 출처는 메모리 fixture로 구성했다. 실제 추출 DB의 Fact 상태를 조회한 것이 아니며 실제 RAG 검색 성공이나 법률 E2E 정확성을 입증하지 않는다. 첫 재현에서 약정 기간 원문 자체는 CONDITIONAL이었지만, 일반 종료 의무 조항 하나만으로 VERIFIED가 되는 별도 반례를 확인했다. 모든 기간 표현이 항상 VERIFIED가 된다고 보고하지 않는다.

## 5. 기존 완료보고서와 현재 동작의 불일치

1. `docs/development/P0_4_2_FINAL_CASE_INDEPENDENCE_REPORT.md`는 엄격 사실 검증과 동적 요건사실에 따른 법률 판단 무결성을 보고한다. 그러나 문서의 일반 조항이 실제 종료 사건으로 승격되는 반례가 현재 남아 있다. 고정된 이름·금액 제거와 법률 전제의 일반화는 서로 다른 작업이다.
2. `docs/code-audit/p0-followup/06_FINAL_REPORT.md`는 질문 맥락과 무관한 임차권등기 안내가 개선되었다고 보고한다. 현재 최종 조립기의 기본 행동 목록에서는 검증 쟁점이 없어도 동일 조치를 출력한다. 과거 특정 테스트의 통과 사실을 부정하는 것은 아니지만, 완료 주장의 적용 범위를 현재 전체 출력 경로로 확대해서는 안 된다.
3. 이번에도 관련 기존 테스트는 통과했다. 테스트 통과만으로 증거 일부 등록 단계의 사실 분석이 검증되었다고 보고하지 말라.

기존 산출물과 소스는 수정하지 않고 이 문서로 불일치를 보고한다.

## 6. E01~E03 단계에서 기대하는 답변 예시

다음은 입력 범위에 맞춘 응답 형태 예시이며 법률 검토 완료 Gold 또는 실제 모델 재실행 결과가 아니다.

> E01에 따르면 임대인은 박정훈, 임차인은 이수현이며 목적물은 주거용 가람오피스텔 503호입니다. 보증금은 3억 원, 월 차임은 없고 최초 약정 기간은 2022년 3월 1일부터 2024년 2월 28일까지입니다.
>
> E02에는 임차인이 임대인에게 계약금 3천만 원과 잔금 2억7천만 원을 지급한 내역 및 잔금 수령 확인 회신이 기재되어 있어, 등록 자료상 보증금 3억 원 지급이 뒷받침됩니다. 이는 임대인이 보증금을 일부 반환했다는 자료가 아닙니다.
>
> E03에는 입주·전입·확정일자 기록이 있습니다. 임차인의 권리를 검토하는 데 중요한 자료이지만 현재 점유·전입 유지 부분은 임차인 진술로 적혀 있고 공식 원본은 별도 확인이 필요합니다. 대항력·우선변제권의 취득과 현재 유지, 다른 권리와의 우열은 관련 요건과 등기자료를 대조하여 판단해야 합니다.
>
> 최초 약정 기간은 지났으나 갱신·해지 통지·합의·도달 자료가 없어 현재 계약 종료와 반환 채무의 이행기를 확정할 수 없습니다. 우선 갱신 경위, 종료 관련 통지와 수신 내역, 현재까지의 반환 내역, 주민등록 초본·확정일자 확인 자료 및 최신 등기사항을 확인해야 합니다.

## 7. 수정 담당자에게 전달할 지시

이번 작업 범위를 아래 결함 수정과 검증으로 제한하고 다음 세부 단계로 자동 진행하지 말라. 모델·Gold·전체 시나리오를 동시에 변경하여 평가 조건을 바꾸지 말라.

1. **거래 방향과 질의 행위를 분리하라.** 임차인→임대인 지급과 반대 방향 반환을 별개 거래로 표현하라. ‘자료를 분석해 달라’는 요청에서 새 입금 사실을 생성하지 말라. 변동은 새 진술·새 증거 및 이전 상태와의 실제 차이가 있을 때만 생성하라. resolved_query도 사용자 미진술 사실의 근거로 사용하지 말라.
2. **일반 조항·예정·조건부 명제·실제 사건을 구분하라.** ‘계약 종료 시 반환한다’는 조항은 실제 종료를 입증하지 않는다. ‘묵시적 갱신 정보 없음’을 ‘묵시적 갱신 아님’으로 바꾸지 말라. 기간 경과, 갱신 유형, 통지·도달·합의 등을 구조적으로 검증하라.
3. **검증 결과의 의미를 최종 문장까지 유지하라.** 종료 사유·효력일·이행기·미반환액을 각각 보존하고, VERIFIED 불리언 하나로 새 확정 문장을 만들지 말라. 조립 단계에서 추가한 법률 주장과 행동도 검증 대상이어야 한다.
4. **질문 유형과 현재 증거 단계에 맞게 답하라.** 기초 사실 정리 요청에는 당사자·목적물·약정·지급·권리 검토 조건·미확인 항목을 우선하라. 종료·미반환이 미확정이면 즉시 소송·임차권등기·지연손해금 청구를 현재 실행 지시로 제공하지 말라. 위험 예방 안내는 그 전제를 명시하라.
5. **미확인을 명시적으로 계산하라.** gap 레코드가 없다는 이유로 충분하다고 출력하지 말라. E03의 당사자 진술 및 원본 미제출도 반영하라. 반환 증거가 없다는 사실을 반환이 전혀 없다는 확정 사실로 취급하지 말라.
6. **항목별 사실 커버리지를 보장하라.** 사용자 원질문을 기준으로 핵심 사실을 선택하고 일반 조항·문서 제목이 당사자와 계약 기간을 밀어내지 않게 하라. 각 사실에 실제 증거·발췌·신뢰 상태를 연결하라.
7. **출처의 각 단계를 대조하라.** 백엔드 본문→저장→API→화면→복사에서 E01~E03 이름·증거 ID가 유지되는지 검사하라. 빈 문자열 부분 일치를 차단하고 법령은 이름 나열이 아니라 해당 주장을 지지하는 조문과 연결하라.

필수 회귀 사례:

- 새 사건·E01~E03·이전 대화 없음·이번 질문 원문: 일부 반환 진술을 생성하지 않음.
- 같은 증거로 이전 대화가 있는 경우, ‘입금’을 ‘이체’로 바꾼 경우: 분석 목적과 지급 방향 유지.
- E01 제4조만 검증된 Fact로 제공: 실제 계약 종료 VERIFIED 금지.
- 최초 약정 기간 경과·갱신 정보 없음: 현재 종료 및 반환 지체 확정 금지.
- 실제 갱신·해지 증거를 추가하면 그 증거 범위에서만 상태 변경. 미등록 E04~E18·평가자 자료 유입 금지.
- 사용자로부터 실제 일부 반환 진술이 들어온 경우: 진술 존재와 증빙 여부를 구분하고 지급 내역과 혼동하지 않음.
- 검증 쟁점 0건 또는 종료 CONDITIONAL: 즉시 반환 분쟁 조치의 자동 생성 차단.
- gap 미생성 또는 E03 원본 없음: ‘기본 요건사실 충실’ 자동 출력 금지.
- 이름·금액·기간·목적물을 바꾼 사건에서도 같은 원칙 유지. 사건 제목의 미반환 문구로 결론 생성 금지.
- 출처 UI 및 복사 결과에 세 증거 이름 표시, 빈 이름으로 다른 증거에 오연결되지 않음.

완료보고에는 수정 전 반례, 수정 후 결과, 실제 실행 명령, 새 trace가 있는 실제 서비스 검증 여부를 구분하라. 한국어 주석 표준을 지키고, 새 외부 의존성이 필요하면 호환성을 확인하여 `backend/requirements.txt`와 `backend/pyproject.toml`을 함께 갱신하라. 이번 검토는 소스 변경이 없어 주석 표준 적용 대상 신규·수정 소스가 없고 의존성 추가도 없다.
