# SC-001 가압류 질의 답변 실패 분석

- 분석일: 2026-10-31 (한국시간)
- 대상: [Langfuse trace 8fe8f0be-cd77-42bf-bab6-d80d2bc149ee](http://127.0.0.1:3001/project/cmv56sw2u00063wm9ivtyrtdj/traces/8fe8f0be-cd77-42bf-bab6-d80d2bc149ee?timestamp=2026-10-31T03%3A13%3A26.447Z)
- 질문: 은행 가압류 7,200만 원을 2026년 8월 12일 발견한 뒤 보증금 반환 위험과 기존 권리분석·대응의 재평가 요청.

## 1. 결론

**공식 법령 조회 실패가 아니라, 주장 분류·검증 후처리·재작성·종료 정책이 함께 만들어 낸 답변 제공 실패다.**

검색은 공식 조문 30개를 확보했고, 검증 모델에도 사건 문서 10개와 기존 RAG 법령 6개를 포함한 전체 46개 출처 본문이 전달됐다. 하지만 검증은 네 번 모두 REVISE였고, 검색 후 재작성과 두 번의 추가 수정을 거친 뒤 WITHHELD로 끝났다. 최종 반환은 398자의 보류 문구와 내부 지적사항이며, 출처는 빈 배열이다.

이전의 '검증 부족인데 성공 답변처럼 노출'과는 구분해야 한다. 이번에는 답변을 막는 정책이 작동했으나, 검증의 오탐·수정 과정의 퇴행·유용한 내용을 모두 버리는 정책 때문에 사용자에게 제대로 된 분석을 제공하지 못했다. 그렇다고 마지막 초안을 그대로 공개하거나 검증을 일괄 완화해도 되는 상태는 아니다.

## 3. 확인된 결함

### P0-1. 사건의 위험 평가를 법률 효과로 오분류하고 후처리가 근거 없음으로 바꾼다

명확한 예는 중개 메모의 호가 범위와 계약 보증금의 차이로부터 '새 임차인 보증금만으로 전액 반환이 어려울 가능성'을 설명한 문장이다.

1. 검증 모델은 이를 `LEGAL_APPLICATION / INFERENCE / SUPPORTED`로 반환했다.
2. 근거에는 사건 문서 E08을 연결했다.
3. `agents/verification.py:922` 부근은 법률 유형에 법령·판례 source_id가 없으면 `UNSUPPORTED`로 변경한다.
4. 그러나 '자료에 부합한다', '추론 근거가 있다'는 기존 reason은 바꾸지 않는다.

그 결과 작성자는 **자료가 뒷받침한다고 설명하면서 동시에 근거 없음으로 처리한 수정 지적**을 받는다. 법령 검색을 늘려도 특정 사건의 자금사정 추론을 입증하는 조문이 생기지는 않는다.

저장된 모델 응답을 그대로 반환하도록 모델 호출만 대체하고, 실제 검증 함수를 실행했다. 세 회차 모두 처리 후 claims가 trace 기록과 완전히 일치했다.

| `515d5060-c8b4-4b70-8995-e3b6eb62c7d7` | 2 | 예 |

이는 모델을 새로 호출한 재실행이 아니라 **기록된 모델 출력에 대한 코드 후처리 재현**이다. 원래 모델도 각 회차를 REVISE로 반환했으므로, 이 후처리만 제거하면 PASS가 된다는 결론은 성립하지 않는다.

또한 '채권 자체가 사라지지는 않지만 회수 위험은 커졌다'처럼 법률 효과와 사건 평가가 한 문장에 섞인 경우도 있다. 이런 혼합 문장은 법률 부분과 사실 추론 부분을 분리해 검증해야 한다. `INFERENCE`라는 이유만으로 모든 문장을 통과시키면 안 된다.

### P0-2. 발견일과 접수일을 모순으로 오인하며, 재작성은 이전의 올바른 구분을 잃는다

사용자 표현은 **8월 12일에 가압류를 발견했다**는 것이다. 증거 E09의 **7월 18일은 등기 접수일**이다. 날짜의 의미가 다르므로 두 값만으로 충돌이라고 판정할 수 없다.

검색 후 초안과 그 다음 수정본은 발견일과 접수일을 명시적으로 구분했다. 마지막 수정본에서는 발견일 설명이 빠졌다. 마지막 검증은 이를 단순 설명 누락을 넘어 '날짜 불일치', '별도 사건인지 확인해야 한다'는 문제로 확대했다.

최종 사용자 답변은 이 내부 지적을 그대로 전달한다. 사용자가 적은 '발견'이라는 의미를 보존하지 못한 검증 오탐과, 수정을 반복하면서 정상 내용을 잃는 작성 문제의 결합이다.

관련 코드: `agents/document_answer.py:96`의 수정 지적 전달, `workflows/document_consultation.py:75` 부근의 전체 답변 재작성. 현재는 회차별 수정 사항과 이미 충족된 항목을 별도 상태로 보존하지 않는다.

### P0-3. 최종 보류가 확인된 사실까지 폐기하고 내부 피드백을 그대로 출력한다

`workflows/document_consultation.py:190`의 `finish_answer`는 전체 PASS가 아니면 다음과 같이 처리한다.

- `missing_legal_issues + missing_issues`를 사용자 답변에 붙인다.
- 출처를 빈 배열로 바꾼다.
- 답변 전체를 WITHHELD로 처리한다.

그래서 이번 답변에는 '밝혔어야 한다', '설명이 제한적이다' 같은 검토자용 표현이 남고, 확인된 가압류 메모의 내용, 기존 자료와의 관계, 추가로 필요한 구체적 자료 설명은 사라졌다. 이미 확인한 부분을 사용자에게 유용하게 전달하는 경로가 없다.

개선 시에는 미검증 초안을 그대로 열어서는 안 된다. 확인된 사실·허용 가능한 조건부 설명·판단 불가 항목을 분리해 축약 답변을 구성하고, **실제로 전달할 그 답변을 다시 검증**해야 한다.

### P1-1. 많은 조문을 찾지만 쟁점 충족을 확인하지 못하고, 후속 검색도 막힌다

이번 공식 검색에는 필요한 주택임대차보호법 제3조·제3조의2 등이 포함됐다. 동시에 다음처럼 질문과의 관련성이 낮은 조문도 섞였다.

- 민법 제812조: 혼인의 성립
- 민법 제1037조: 상속재산의 경매
- 민사집행법 제270조: 자동차 등에 대한 경매

`tools/official_statute_search.py:243` 이후는 질문과 누락 쟁점을 합쳐 키워드 점수를 매기고 법별 상위 항목을 선택한다. `workflows/legal_workflow.py:1442`에서는 법마다 10개를 요청한다. 검색 결과 개수와 핵심 쟁점 충족 여부는 별개지만 후속 분기는 결과 유무만 본다.

마지막 검증에서 추가 법리와 시행령 부족을 언급했어도 `document_consultation.py:181`의 `not hilt_executed` 조건 때문에 검색으로 돌아갈 수 없다. 로컬 분기 확인에서도 `hilt_executed=True`, 새 법령 부족, 수정 횟수 1인 상태는 검색 대신 `revise`를 반환했다.

이번 마지막 검증에는 `missing_legal_issues`가 있는데 reason_code는 `ANSWER_REVISION_REQUIRED`다. 부족한 법령, 사실 자료, 표현 수정이 단일 reason_code에 섞여 있는 점도 개선해야 한다.

법령명 정규화는 앞선 검색어 오류를 고치지만, 이 검색 관련성·쟁점 충족 문제까지 해결하지 않는다.

### P1-2. 검증 범위가 확대되면서 실제 답변 오류도 제대로 고쳐지지 않는다

마지막 검증은 소액임차인 최우선변제 관련 시행령 부족을 새로 제시한다. 사용자가 직접 물은 사항도 아니고 마지막 초안이 그 권리를 적용한 것도 아니다. 필요성이 입증되지 않은 추가 쟁점이 최종 보류 안내에 들어간 것이다.

반대로 실제 초안에는 9월 30일을 지정한 통지가 있는데도 7월 1일 무렵을 법정 해지 효력 시점으로 계속 제시하는 문제가 남았다. 마지막 검증은 두 날짜를 별도로 언급했다는 이유로 expressed_intent를 통과시켰다. **통지 내용의 해석을 해결한 것과 두 날짜를 나란히 적은 것은 다르다.** 이는 trace의 작성 지침에 있는 '지정 종료일을 기계적으로 더 이른 날짜로 바꾸지 말라'는 기준에도 맞지 않는다. 구체적인 종료일의 법률상 정답은 별도 법리 검토가 필요하며, 이 분석에서 확정하지 않는다.

즉, 검증은 오탐으로 답변을 막으면서도 원래 고쳐야 할 해석 문제를 완전히 해결하지 못한다. 단순 PASS 완화나 수정 횟수 증가는 적절한 해결책이 아니다.

### P1-3. 판례 인용 지표에 일반 날짜 문장이 섞인다

마지막 citation audit의 generated/validated citation 목록에는 `PRECEDENT:2024년과2026`이 있다. 실제 판례 인용이 아니라 '2024년과 2026년'이라는 표현이다.

- `agents/verification.py:54`의 사건번호 정규식이 일반 한글 1~3글자를 사건 부호로 허용한다.
- 로컬 재현에서 `2024년과 2026년 모두 별도 재계약서 없이 계속 거주`가 사건번호로 매칭됐다.
- 같은 표현이 사건 자료에도 있으면 `verification.py:391`의 출처 본문 탐색을 통해 알려진 판례번호로 취급될 수 있다.

이 항목은 이번 WITHHELD의 직접 원인이 아니라 **인용 감사 신뢰성의 별도 결함**이다. citation_support_rate=1을 답변 전체의 정확성으로 해석할 수 없다.

## 4. 정상 작동이 확인된 부분과 한계

- 공식 검색: 성공. 이번 trace는 네트워크 실패나 법령명 정규화 실패가 아니다.
- 근거 전달: 최종 검증까지 실제 46개 출처 본문 전달 확인.
- 검증 실패 차단: 작동. 최종 상태는 WITHHELD이며 PASS로 확정한 기록이 아니다.
- API `status=SUCCESS`: 실행 완료 상태다. 답변 판정은 별도 `final_disposition=WITHHELD`다. 프런트엔드에는 WITHHELD 배지 분기가 존재하지만, 이번 분석에서는 브라우저 화면 렌더링을 직접 확인하지 않았다.
- 작성 지침: 실제 작성 입력에 날짜 구분 및 지정일 조기 대체 금지 지침이 들어 있었다. 지침을 적었다는 사실만으로 모델 준수를 보장하지 못했다.
- 답변 분량: 1,200~1,800자 정도라는 지침이 있었으나 초안은 3,481~4,540자였다. 수정 과정에서 초점과 길이를 관리하지 못했다.

## 5. 수정 우선순위와 수용 기준

### 1순위: 검증 계약과 날짜 의미를 바로잡는다

- 문장을 사실, 사건 자료에 근거한 추론, 법률 규칙, 법률 적용, 행동 권고로 분리한다. 혼합 문장은 원자적 주장으로 나눈다.
- 법률 주장에는 법률 근거를 요구하되 사건 위험 추론은 해당 증거와 추론의 한계를 검증한다.
- 후처리가 모델 판정을 바꾸면 원래 판단과 정책 변경 이유를 별도 기록한다. reason을 그대로 둔 채 판정만 바꾸지 않는다.
- 날짜는 사건·행위자·날짜 역할과 함께 비교한다. 접수일/발견일/열람일 차이를 자동 충돌로 보지 않는다.

수용 기준: 이번 세 검증 출력의 후처리 재현에서 오분류 사례를 바로잡고, 실제로 법률 근거가 없는 권리·의무 단정은 계속 차단해야 한다. 동일 접수일을 서로 다르게 주장하는 반례와 발견일/접수일이 다른 정상 사례를 함께 검증한다.

### 2순위: 수정과 추가 검색을 쟁점 단위로 수행한다

- 해결된 항목, 미해결 항목, 새 오류를 회차별로 추적하고 수정 대상 밖의 정상 내용을 보존한다.
- 법령명·조문·법적 쟁점별 검색 계획과 충족 여부를 기록한다. 검색 개수로 충족을 판단하지 않는다.
- 승인 범위 안에서 새로 필요한 근거를 제한적으로 보완하되 동일 검색 반복은 막는다. 범위가 바뀌는 경우는 승인 정책을 적용한다.
- 검색 후 첫 재작성과 오류 수정 횟수의 의미를 분리한다.
- 사용자 질문과 연결되지 않는 새 검증 요구를 차단한다.

수용 기준: 첫 수정본에 있던 발견일/접수일 구분이 뒤 수정본에서 사라지지 않아야 한다. 법령 부족이면 동일 초안만 반복 수정하지 않아야 한다. 새 쟁점의 추가는 사용자 요청과의 연결 근거가 있어야 한다.

### 3순위: 최종 답변을 사용자에게 유용한 결과로 만든다

- 일부 판단이 미확정이면 확인된 사실, 조건부로 설명 가능한 범위, 추가 확인사항을 구분한다.
- 내부 검토자 문구를 그대로 노출하지 않는다.
- 부분 답변도 실제 최종 문장을 다시 검증하고, 검증하지 못한 법률 결론은 남기지 않는다.
- 실행 성공과 답변 품질 상태를 UI·API·평가 지표에서 명확히 구분한다.

수용 기준: 이번 질의에 대해 확인된 자료와 질문에 대한 변화 설명이 포함된 답변을 제공해야 한다. 단순 '확인하지 못했다' 문구나 미검증 전체 초안 공개를 성공으로 세지 않는다. 정확성, 질문 충족, 전달 품질, 지연을 함께 평가한다.

## 6. 수행한 검증과 미수행 항목

| 검사 | 결과 | 의미 |
|---|---|---|
| 대상 trace API 조회 및 generation/노드 대조 | 완료 | 실행 기록 기반 분석 |
| 최종 검증 입력의 46개 출처 ID·본문 존재 확인 | 46/46 | 이 실행의 전달 누락 없음 |
| 기록된 모델 출력 3개에 대한 현재 후처리 재현 | claims 3/3 완전 일치 | 판정 변경 경로 재현 |
| 후속 검색 분기 확인 | 검색 후 신규 누락에도 revise | 단일 검색 제한 확인 |
| 날짜 문장의 판례번호 오인 재현 | 재현됨 | 감사 지표 결함 확인 |
| 이번 문제에 대한 코드 수정·새 모델 전체 재실행 | 미수행 | 개선 완료 또는 POC PASS로 보고하지 않음 |
| 실제 브라우저 화면 검증 | 미수행 | UI 표시는 코드 확인에 한정 |

재현 과정에서 처음에는 관측 decorator의 축약 입력을 함수 입력으로 사용해 실패했다. 해당 args는 문자열 500자로 축약된 값이어서 재현 데이터로 사용할 수 없었다. 이후 완전한 노드 출력의 초안·출처와 실제 generation 출력을 사용해 다시 실행했고 위의 3/3 일치를 확인했다. 축약 입력으로 실패한 시도는 제품 실행 실패로 계산하지 않았다.

이전 법령명 정규화 작업의 잔여 검증도 확인했다. 관련 단위/HILT 검사 25개 통과, 외부 모델에 의존하는 1개 검사는 제외됐다. 실제 법제처 API에서 순수 법령명은 3개 조문, `주택임대차보호법 제3조(대항력 등)`은 제3조 1개, `주택임대차보호법 제3조의2(보증금의 회수 등)`은 제3조의2 1개를 반환했다. 이 결과는 검색어 처리 개선에 한정되며 이번 답변 품질 실패의 해결 증거가 아니다.

이번 산출물은 분석 문서다. 제품 코드 추가 변경 및 신규 의존성은 없으며, 신규·수정 제품 소스에 대한 주석 표준 점검은 해당 없음이다. 기존 작업 파일은 보존했고 배포·서버 재시작·사건 DB 수정은 수행하지 않았다.
