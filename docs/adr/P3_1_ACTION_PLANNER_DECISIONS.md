# Architecture Decision Record: P3.1 Action Planner Decisions

## 1. Context (배경)
P3.1에서는 사용자의 사건을 분석한 결과를 바탕으로 실제 행동 계획(Legal Action Plan)을 생성해야 합니다. 이 과정에서 1) LLM의 자유로운 행동 제안과 2) 법률적 요건/기한의 엄격한 구조적 관리 사이의 균형이 필요합니다.

## 2. Decision 1: Action Catalog 중심의 추천 (Rule + LLM Hybrid)
### 대안 1: LLM이 자유롭게 행동을 생성하게 둔다.
- 장점: 유연함.
- 단점: 예측 불가능성, 환각 발생, UI 컴포넌트 표준화 어려움.

### 대안 2: 고정된 하드코딩 Rule Engine만 사용한다.
- 장점: 100% 예측 가능.
- 단점: 법률 분쟁의 다양한 엣지 케이스 처리 불가, 유지보수 비용 증대.

### 결정: 사전에 정의된 'Action Catalog' 내에서 LLM이 판단하여 추천한다.
- **주택 임대차 분쟁**에 한정하여 (예: 내용증명 발송, 보증금 반환 청구 소송, 임차권등기명령 등) 표준 행동 카탈로그를 정의합니다. LLM은 이 카탈로그 내에서 현재 사건 컨텍스트에 맞는 행동을 선택하고 그 요건 충족 여부를 판단합니다.
- 예기치 않은 행동을 방지하고 프론트엔드에서 각 행동별 표준화된 컴포넌트 렌더링이 가능해집니다.

## 3. Decision 2: Deadline Engine 분리
### 대안 1: LLM에게 날짜를 계산하게 한다 (예: "계약 만료 2개월 전이 언제인가?").
- 단점: LLM의 날짜 산술 계산은 오류 확률이 높음.

### 대안 2: 결정론적(Deterministic) Deadline Engine 도입.
- **결정**: LLM은 '계약 종료일' 등의 기준(Basis)과 적용할 '규칙(예: -2 months)'을 식별하는 역할만 담당합니다. 실제 DateTime 연산은 Python 백엔드 코드가 처리하여 무결성을 보장합니다.

## 4. Decision 3: 데이터베이스 저장 구조 (PostgreSQL 중심)
### 대안 1: 생성된 플랜 전체를 JSON 필드로 하나에 밀어넣는다.
- 장점: 스키마 변경 불필요, 빠른 구현.
- 단점: 각 행동별 상태 변화(COMPLETED 등)를 추적하거나 버전 간 비교가 어려움. 개별 행동에 대한 사용자 상호작용(체크리스트 체크 등) 구현이 힘듦.

### 대안 2: 정규화된 테이블 모델 사용 (`LegalAction`, `ActionRequirement` 등)
- **결정**: Action 자체를 영구적인 엔터티로 분리하여 사용자 상태 저장을 지원합니다.

## 5. Consequences (결과)
- 데이터 모델 복잡도가 증가하지만, 재평가(Revision) 시 기존 사용자의 행동 이력과 상태를 보존할 수 있습니다.
- 법률적 환각 방지와 함께 사용자 친화적인 진행률(Progress) 추적이 가능해집니다.
