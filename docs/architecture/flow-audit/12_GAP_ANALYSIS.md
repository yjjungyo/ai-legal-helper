## 2. 설계 문서 vs 실제 구현의 주요 불일치 (Design vs Implementation Gaps)

1. **ReAct 에이전트 vs 하드코딩된 1회 호출 래퍼 (`base_agent.py`)**
   - 설계상 7개 법률 에이전트는 ReAct(`Thought -> Action -> Observation`) 루프를 돌며 필요한 법령을 검색·추론해야 하나, 실제 `base_agent.py:47-92`는 `create_react_agent`와 `AgentExecutor`를 자체 간이 함수/클래스로 덮어써서 `tools[0].invoke()` 반환값을 버리고 `agent_scratchpad=""`로 1회 LLM 호출만 수행한다.
2. **Adaptive Retrieval 루프 vs 단순 문장 교정 (`legal_workflow.py`)**
   - 설계상 검증 단계에서 근거가 부족하면 검색 쿼리를 재작성하여 ChromaDB/Neo4j를 재검색해야 하나(`EVT-018`), 실제 `revise_node`는 `draft_answer`와 `revision_instructions`만 넣고 LLM에게 문장만 다시 쓰게 한다.
3. **모순 탐지(`CONTRADICTS`) 파이프라인 단절 (`evidence.py`, `evidence_extractor.py`)**
   - DB 스키마(`EvidenceLink.link_type`), Neo4j 관계, 프런트엔드 UI 배너, REST API(`/evidence/conflicts`)는 모두 준비되어 있으나, 정작 증거 추출이나 Claim 검토 시 기존 `Fact`와 비교하여 `CONTRADICTS` 링크나 `CONTRADICTION_CANDIDATE` 상태를 생성하는 비즈니스 로직이 어디에도 없고, `GraphRAG` 임포트 오타까지 겹쳐 있다.
4. **Langfuse 계층적 Trace 설계 vs 평탄화된 Span (`langfuse_client.py`, `decorators.py`)**
   - 설계상 `api_request` -> `process_consultation` -> `run_agents` -> `legal_specialist_agent` -> `rag_retrieve` 순의 트리 구조여야 하나, `_active_spans` 키(UUID)와 `parent_span_id`(노드명 문자열) 타입 불일치로 모든 Span이 루트 아래에 평탄화되어 기록된다.
