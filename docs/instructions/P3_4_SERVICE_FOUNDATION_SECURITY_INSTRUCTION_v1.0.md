# AI Legal Helper — P3.4 Service Foundation & Security 개발지시서 v1.0

**프로젝트:** `C:\myprjs\ai-legal-helper`  
**개발 단계:** P3.4  
**목표:** AI Legal Helper를 실제 사용 가능한 서비스로 운영하기 위한 인증, 권한, 개인정보 보호, 파일 관리, 감사 로그 및 장애 대응 기반을 구축한다.

## 1. 개발 원칙

1. P0~P3.3의 기존 기능과 아키텍처를 유지한다.
2. `C:\myprjs\ai-legal-agent` 원본 프로젝트는 절대 수정하지 않는다.
3. 기존 코드와 DB 모델을 먼저 조사하고 중복 구현을 피한다.
4. PostgreSQL을 사용자·사건·권한·감사 이력의 Source of Truth로 사용한다.
5. 모든 사건 데이터 접근은 서버에서 사용자 권한을 검증한다.
6. React에서 버튼을 숨기는 것만으로 권한을 통제하지 않는다.
7. 개인정보와 인증 정보가 로그, 오류 메시지, URL 등에 노출되지 않도록 한다.
8. 실제 법률 분석 정확도 평가는 전체 개발 후 진행한다.
9. 이번 단계에서는 인증·권한·파일·운영 기능의 기본 테스트를 수행한다.
10. `AGENTS.md` 및 `docs/development/CODING_COMMENT_STANDARD.md`의 한국어 주석 규칙을 준수한다.

## 2. 사전 코드 조사

구현 전에 다음을 확인한다.

- 기존 사용자 및 인증 모델 유무
- 기존 Case 소유자 정보
- Evidence 파일 저장 구조
- Document Export 파일 저장 구조
- FastAPI 라우터 및 의존성 구조
- React Router 및 상태 관리
- PostgreSQL 마이그레이션 상태
- 현재 Docker Compose 서비스
- API 키와 비밀정보 관리 방식

기존 구조와 충돌하는 변경은 피하고, 필요한 마이그레이션 계획을 먼저 작성한다.

## 3. 사용자 인증

### 필수 기능

- 회원가입
- 로그인
- 로그아웃
- 현재 로그인 사용자 조회
- 비밀번호 변경
- 인증 만료 처리

### 보안 요구사항

- 비밀번호는 Argon2id 등 검증된 비밀번호 해시로 저장한다.
- 평문 비밀번호를 저장하거나 로그에 기록하지 않는다.
- 로그인 실패에 대한 속도 제한을 적용한다.
- 인증 토큰은 안전하게 관리한다.
- 브라우저 저장소(localStorage)에 장기 인증 토큰을 저장하지 않는다.
- 가능하면 HttpOnly, Secure, SameSite 속성을 가진 쿠키 기반 세션을 적용한다.
- 쿠키 기반 인증에는 CSRF 방어를 적용한다.
- 로그아웃 시 서버에서 세션을 무효화한다.
- 인증 만료 시 프런트엔드에서 안전하게 로그인 화면으로 이동한다.

인증 방식을 선택한 이유와 대안을 ADR에 기록한다.

## 4. 사용자 및 세션 모델

기존 모델을 조사한 후 필요한 항목을 추가한다.

### User

- `id`
- `email`
- `password_hash`
- `display_name`
- `status`
- `created_at`
- `updated_at`

### UserSession

- `id`
- `user_id`
- `session_token_hash`
- `expires_at`
- `revoked_at`
- `created_at`

필요하다면 별도 로그인 실패 기록 모델을 추가한다.

토큰 원문을 DB에 저장하지 않는다.

Alembic 마이그레이션을 적용한다.

## 5. 사건별 접근 권한

모든 Case는 소유자를 가져야 한다.

### 필수 정책

- 사용자는 자신의 사건만 조회할 수 있다.
- 자신의 사건만 수정하거나 삭제할 수 있다.
- 다른 사용자의 사건 ID를 직접 입력해도 접근할 수 없어야 한다.
- 사건에 속한 Fact, Timeline, Evidence, Action, Document도 동일한 접근 통제를 적용한다.
- GraphRAG 검색과 ChromaDB 검색에도 사건별 데이터 분리를 적용한다.
- 비동기 작업과 GraphSync Worker에도 사건 소유권 및 실행 권한의 경계를 유지한다.

FastAPI에 공통 인증·인가 Dependency를 구현한다.

기존 엔드포인트를 전수 조사하여 접근 통제를 적용한다.

다른 사용자의 자원은 존재 여부를 불필요하게 노출하지 않도록 처리한다.

## 6. 기존 사건 데이터 마이그레이션

현재 개발 DB에 소유자가 없는 사건이 존재할 수 있다.

이를 자동으로 임의 사용자에게 할당하지 않는다.

다음 중 안전한 방법을 설계한다.

- 관리자 전용 소유권 이전 절차
- 기존 개발 데이터의 명시적 소유자 지정
- 테스트 데이터의 분리 또는 초기화

마이그레이션 전 백업과 복구 방법을 기록한다.

운영 데이터가 존재하는 경우 파괴적인 자동 삭제를 금지한다.

## 7. 파일 저장 및 접근 통제

대상:

- 계약서
- 통화 녹취록 및 텍스트
- 증거 PDF/DOCX/TXT
- 생성된 법률문서
- DOCX/PDF 출력 파일

### 필수 기능

- 인증된 업로드
- 사건 소유권 확인
- 안전한 파일명 처리
- 파일 크기 제한
- 허용 확장자 및 실제 파일 형식 검증
- 다운로드 권한 검증
- 삭제 정책
- 임시 파일 정리
- SHA-256 무결성 확인

파일은 공개 정적 디렉터리에 두지 않는다.

파일 경로를 API 입력값으로 직접 신뢰하지 않는다.

경로 탐색 공격을 차단한다.

파일 삭제 시 DB 메타데이터와 실제 저장 파일의 정합성을 관리한다.

향후 오브젝트 스토리지로 이전할 수 있도록 Storage Service 인터페이스를 분리한다.

- 로그인 성공 및 실패
- 사건 생성·수정·삭제
- 증거 업로드·승인·반려·삭제
- AI 분석 실행
- Action Plan 생성 및 변경
- 법률문서 생성·수정·승인·출력
- 접근 거부
- 중요 설정 변경

### AuditLog 예시

- `id`
- `actor_user_id`
- `case_id`
- `event_type`
- `resource_type`
- `resource_id`
- `result`

일반 사용자에 의한 감사 로그 수정·삭제를 금지한다.

## 11. 서비스 상태 점검

다음 API를 제공한다.

- `/health/live`
- `/health/ready`

Liveness와 Readiness를 구분한다.

Readiness는 서비스에 필수적인 의존성을 확인한다.

선택적 의존성 장애는 서비스 정책에 따라 DEGRADED 상태로 표시한다.

API 응답에 DB 접속 문자열이나 API 키를 포함하지 않는다.
