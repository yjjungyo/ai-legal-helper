# AI Legal Helper — P3.3 Case Workflow & UX Integration 개발지시서 v1.0

**프로젝트:** `C:\myprjs\ai-legal-helper`  
**개발 단계:** P3.3  
**목표:** 사건 등록부터 AI 상담, 증거 관리, 법률 분석, 대응 계획, 문서 작성까지 전체 사용자 흐름을 통합한다.

## 1. 기본 원칙

- 기존 P0~P3.2 기능과 데이터 모델을 최대한 재사용한다.
- `C:\myprjs\ai-legal-agent` 프로젝트는 수정하지 않는다.
- 기능을 중복 개발하지 않고 기존 기능을 통합한다.
- React + TypeScript, FastAPI, LangGraph, PostgreSQL, ChromaDB, Neo4j 구조를 유지한다.
- 기존 개발지시서 버전 관리와 한국어 주석 표준을 준수한다.
- 실제 법률 정확도 및 사용자 만족도 평가는 전체 개발 완료 후 수행한다.
- 이번 단계에서는 기본 기능 테스트, API 연동 테스트, 회귀 테스트를 수행한다.
- 개발 과정에서 미완성 기능은 숨기지 않고 명확히 표시한다.

## 2. 통합 사용자 시나리오

다음 시나리오를 처음부터 끝까지 수행할 수 있도록 개발한다.

1. 사용자가 새로운 사건을 등록한다.
2. AI와 대화하며 사건 내용을 설명한다.
3. AI가 사건 사실, 당사자, 날짜, 금액을 추출한다.
4. 사용자가 추출된 사실을 확인하고 수정한다.
5. 계약서 및 관련 증거를 업로드한다.
6. AI가 증거를 분석하고 사건 타임라인을 구성한다.
7. 사용자가 법률 분석을 요청한다.
8. AI가 주요 쟁점, 관련 법률 근거, 부족한 정보를 제시한다.
9. 사용자가 대응 계획을 생성한다.
10. 대응 행동 중 하나를 선택하여 법률문서 초안을 작성한다.
11. 사용자가 문서를 검토하고 수정한다.
12. 문서를 저장하거나 지원되는 형식으로 다운로드한다.
13. 사건을 다시 열어 이전 작업을 이어간다.

## 3. 통합 Case Workspace

기존 UI를 검토하고 하나의 사건 중심 화면으로 정리한다.

### 화면 구성

- 사건 목록 및 신규 사건 등록
- 사건 개요
- AI 상담
- 사실관계 및 타임라인
- 증거 관리
- 법률 분석
- Evidence Graph
- Action Plan
- Documents
- 사건 활동 이력

### UX 요구사항

- 사용자는 현재 어느 사건을 작업 중인지 항상 알 수 있어야 한다.
- 기능 간 이동 시 사건 정보가 유지되어야 한다.
- 저장되지 않은 입력이 있으면 경고한다.
- 분석 진행 상태, 성공, 실패를 구분한다.
- 사용자가 동일한 정보를 반복 입력하지 않도록 한다.
- 사건 수정 시 관련 분석 결과의 재검토 필요 여부를 표시한다.
- 비어 있는 화면에는 다음 행동을 안내한다.
- 전문 용어에는 이해하기 쉬운 설명을 제공한다.

## 4. AI 상담과 사건 데이터 연계

기존 채팅 기능과 Case Intelligence를 연결한다.

- 채팅은 현재 사건 ID를 기준으로 관리한다.
- 대화 내용에서 사실 후보를 추출한다.
- 추출 결과를 사용자에게 보여준다.
- 사용자가 승인한 사실만 확정 사실로 반영한다.
- 채팅에서 언급한 날짜·금액·당사자가 사건 정보와 충돌하면 표시한다.
- 사건 정보 수정 시 관련 분석이 오래된 상태임을 표시한다.

기존 데이터 모델을 우선 재사용하고 필요한 경우에만 확장한다.

## 5. Workflow Orchestrator

기존 LangGraph 워크플로우와 API를 조정하여 사건별 전체 작업 흐름을 지원한다.

상태 예시:

- `CASE_CREATED`
- `FACTS_IN_REVIEW`
- `EVIDENCE_IN_REVIEW`
- `READY_FOR_ANALYSIS`
- `ANALYSIS_COMPLETED`
- `ACTION_PLAN_READY`
- `DOCUMENT_DRAFTED`

이 상태는 UI 진행 안내용이며, 기존 도메인 상태와 충돌하지 않도록 별도로 설계하거나 매핑한다.

사용자가 반드시 정해진 순서로만 작업하도록 강제하지 않는다.

작업 순서가 달라도 사건 데이터의 정합성이 유지되어야 한다.

## 6. 통합 API

기존 엔드포인트를 조사한 후 필요한 API만 추가한다.

- 사건별 Workspace 요약 조회
- 사건별 작업 진행 상태 조회
- 사건별 최근 활동 이력
- 사건별 분석 실행 상태 조회
- 재분석 필요 항목 조회
- 기능별 작업 시작 및 결과 조회

기존 API를 중복 구현하지 않는다.

API 오류 형식과 프런트엔드 오류 표시 방식을 통일한다.

## 7. 상태 관리 및 비동기 작업

LLM 분석 및 문서 생성은 처리 시간이 길어질 수 있다.

다음 기능을 구현한다.

- 분석 시작 시 진행 상태 표시
- 중복 요청 방지
- 실패 시 오류 원인 표시
- 재시도 기능
- 화면 이동 후 작업 상태 복원
- 완료된 결과의 사건별 저장

기존 백그라운드 작업 구조를 조사하여 재사용한다.

브라우저가 닫히거나 새로고침되더라도 서버에서 완료된 작업 결과를 조회할 수 있어야 한다.

## 8. Evidence Graph UI 연결

기존 Evidence Graph를 사건 분석 화면과 연결한다.

- 사건별 그래프 조회
- Fact, Evidence, Claim, LegalIssue 관계 표시
- 그래프 노드 선택 시 상세 정보 표시
- 관련 원본 증거 이동
- 승인되지 않은 증거 상태 구분
- 그래프 데이터가 없거나 Neo4j 장애가 발생한 경우 안내

## 9. Action Plan 및 Documents 연결

P3.1과 P3.2 기능을 하나의 사용자 흐름으로 연결한다.

- 추천 행동에서 문서 작성 선택
- 선택한 Action ID를 문서 생성 API에 전달
- 문서 작성 화면에서 관련 사실과 증거 표시
- 작성된 문서를 해당 Action과 연결
- 문서 저장 후 Action Plan으로 복귀 가능
- 사건을 다시 열었을 때 작성 중인 문서 복원

기존 Document Generator에서 지원하지 않는 출력 형식은 지원되는 것처럼 표시하지 않는다.

## 10. 오류 처리

다음 상황을 처리한다.

- PostgreSQL 연결 실패
- Neo4j 연결 실패
- ChromaDB 검색 실패
- Azure OpenAI 호출 실패
- 문서 생성 실패
- 증거 파일 파싱 실패
- 잘못된 사건 ID
- 존재하지 않는 문서 ID
- 네트워크 일시 중단
- 중복 클릭 및 중복 요청

사용자가 이해할 수 있는 한국어 오류 메시지를 제공한다.

내부 스택 트레이스와 개인정보는 사용자 화면에 노출하지 않는다.
