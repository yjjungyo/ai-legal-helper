# RAG 검색·검증·최종 답변 정합성 수정 지시문 v1.0

- 작성일: 2026-10-17
- 상태: 구현 지시문. 구현 완료 또는 전체 테스트 통과 보고서가 아니다.
- 대상: ai-legal-helper의 법률 상담 검색, 검증, 복구, 최종 출력 경로
- 작성 범위: 문서 작성만 수행. 소스코드·환경설정·DB·모델 배포는 변경하지 않았다.

## 1. 작업 지시

법률 근거가 부족하거나 적용 법령이 잘못된 답변을 검증된 결론처럼 제공하지 않도록 수정하라. 검색 결과의 출처를 검증 단계까지 보존하고, 복구 가능한 검증 실패는 제한적으로 재검색·재작성·재검증하라. 해결되지 않으면 검증 지적사항과 확인 가능한 내용만 사용자에게 전달하라.

이미 추가된 기능은 다시 만들지 말고 실제 동작과 아래 수용 기준의 차이를 확인하여 보완하라. 작업 중 변경된 파일과 기존 사용자 변경을 보존하라. 이 문서가 별도 P2/P3 단계 진행이나 모델 전환을 승인하는 것은 아니다.

## 2. 문제의 근거와 시점 구분

### 2.1 실제 트레이스에서 확인한 현상

- Trace: `trace-t-ar-01-6db48d7e`
- 주소: http://localhost:3001/project/cmv56sw2u00063wm9ivtyrtdj/traces/trace-t-ar-01-6db48d7e?timestamp=2026-10-16T15%3A10%3A38.001Z
- 이름: `Verification:T-AR-01`. 일반 API 요청과 동일한 실행 경로라고 단정하지 않는다.
- 주택 임대차 묵시적 갱신 후 해지 질문에 민법 제635조·제636조가 검색되었다.
- 전문가 답변과 종합 답변이 민법의 일반 규정을 적용하여 1개월이라는 결론을 제시했다.
- 검색 관찰값에는 실제 문서가 있었지만 검증 입력의 구조화된 출처 목록은 `[]`였다.
- Verification은 `INSUFFICIENT`, 주요 주장 6개는 모두 `UNSUPPORTED`로 평가했다.
- 해당 트레이스에는 재작성 노드 실행이 없었고, 마지막 안내에 잘못된 결론과 예시가 남았다.

이 사례의 문제는 가짜 파일명을 생성했다는 데 있지 않다. 실제 검색된 민법 문서를 해당 주택 임대차 사안의 충분한 근거로 취급한 점과 검증 실패가 답변의 결론을 통제하지 못한 점이다.

### 2.2 현재 코드에서 확인한 변경과 잔여 위험

2026-10-17 재확인한 코드에는 이미 적응형 재검색, 공식 법령 검색, 검색 승인 경로와 검증 지적사항 표시가 추가되어 있다. 따라서 과거 트레이스만으로 현재 코드에 재검색 기능이 전혀 없다고 보고하지 말라.

그러나 다음 잔여 위험은 별도로 해결·검증해야 한다.

- `agents/verification.py`: LLM 검증 예외 시 인용 결함이 없으면 `PASS`를 반환하는 폴백이 있다.
- `workflows/legal_workflow.py`: 검증 상태 누락 시 기본값이 `PASS`다.
- 같은 파일: 검증 노드가 `retrieved_sources`를 검증 후 출처 목록으로 대체한다.
- 같은 파일: 근거 부족 안내 뒤에 `sanitized_draft` 전체를 참고 초안으로 붙인다. 경고가 있어도 잘못된 법률 결론은 남는다.
- 현재 공식 법령 검색·승인 경로의 존재만으로 실제 원문 확보와 답변 정확성이 증명되지는 않는다.

현재 연결된 민사 컬렉션의 메타데이터 확인에서는 1,210개 문서가 모두 민법으로 분류되었고 주택임대차보호법 원문은 확인하지 못했다. 다른 법령의 언급은 해당 특별법 원문 확보와 다르다. 이 확인은 현재 DB 기준이며 과거 트레이스 시점의 DB 구성을 증명하지 않는다.

### 2.3 격리 재현에서 얻은 결론

- 실제 `Tool.invoke` 경로와 ContextVar를 사용한 격리 재현에서 검색 텍스트는 프롬프트에 들어갔지만 출처 목록은 상위 실행 흐름에 전달되지 않는 문제가 확인되었다. `.func` 직접 호출만 검사해서는 이 문제를 잡을 수 없다.
- 검색된 두 민법 출처를 복원하면 결정적 인용 검사 지표가 개선되어도 잘못된 1개월 결론은 그대로 남았다. 이는 전체 LLM 검증의 PASS를 확인했다는 의미가 아니다.
- 같은 파일·같은 페이지의 다른 조문이 동일한 출처 ID로 합쳐질 수 있다. 출처 전송, 출처 식별, 법률 내용 검증은 각각 해결해야 한다.

## 3. 필수 구현 요구사항

### 3.1 검색 결과의 명시적 전달

검색 도구가 검색 텍스트와 구조화된 출처를 함께 반환하도록 하라. 반환 envelope 또는 도구 artifact 등 현재 LangChain과 호환되는 방식을 선택하되, Executor가 실제 결과를 수집하여 전문가 결과와 워크플로우 상태로 전달해야 한다.

ContextVar 내부에서 목록을 교체한 뒤 상위 컨텍스트에서도 변경되리라 가정하지 말라. 전역 가변 목록으로 우회하지 말라. 동시 요청 간 출처 혼합을 금지한다. 도구 호출 실패와 검색 결과 0건을 구분하라.

### 3.2 출처 ID와 원본 보존

- 문서·버전·컬렉션·청크를 구분할 수 있는 안정적인 ID를 사용하라. 같은 페이지의 서로 다른 조문을 보존하라.
- 재검색 결과 병합은 실제 동일 출처만 중복 제거하라. 재검증 시에도 다른 조문이 사라지지 않아야 한다.
- 원본 검색 목록, 인용에 사용한 목록, 검증된 목록, 거절 사유를 분리하라. 검증 결과로 원본 목록을 덮어쓰지 말라.
- 페이지·청크·조문이 실제 출처와 일치하는지 검사하라. 파일명만 일치한다고 잘못된 페이지를 승인하지 말라.
- 기존 `file`, `file_name` 표시 호환성을 유지하고 새 출처 ID와 연결하라.
- 실제로 확인되지 않은 URL, 시행일, 버전, 조문을 만들어 넣지 말라.

### 3.3 특별법 원문 확보

특별법 적용 여부가 핵심인데 현재 컬렉션에 원문이 없으면 같은 민법 컬렉션을 반복 검색하는 것으로 복구를 완료 처리하지 말라.

기존 공식 법령 검색 기능을 먼저 검토하여 공식 원문을 실제로 확보하거나, 필요한 최소 법령을 검증된 절차로 수집하는 경로를 완성하라. 출처 URL, 법령명, 조문, 시행·버전 정보, 조회 시각과 내용 식별 정보를 가능한 범위에서 보존하라. 필요한 사건 시점과 적용 법령의 시점을 구분하라.

승인 대기·거절·만료·검색 실패·원문 미확보를 명시적으로 처리하라. 현재 승인 경로를 유지할 경우 중단·재개 상태가 API와 화면에 일관되게 전달되어야 한다. 무제한 승인 대기나 재검색 루프를 만들지 말라.

인증·네트워크·외부 서비스 제약으로 원문을 확보하지 못하면 실제 E2E 검증은 `NOT_TESTED` 또는 `BLOCKED`로 보고하라. 테스트 fixture만으로 운영 코퍼스 보강을 완료했다고 보고하지 말라.

### 3.4 법률 검증의 분리

다음 검사를 별도 결과로 관리하라.

1. 출처 존재: 실제 요청에서 확보한 문서인가.
2. 인용 일치: 문서·페이지·조문·청크가 맞는가.
3. 내용 지지: 인용 본문이 해당 주장의 조건·기간·수치·기산점·효과를 뒷받침하는가.
4. 적용 가능성: 일반법과 특별법, 사건 유형, 당사자 지위, 사실관계, 적용 시점이 맞는가.

단어 중복과 조문 번호 일치는 법률적 타당성을 증명하지 않는다. 출처 존재율을 법률 정확도로 표시하지 말라. 검사할 주장이 0개라는 이유로 정확도 100% 또는 자동 PASS를 부여하지 말라.

### 3.5 검증 상태를 보수적으로 처리

- 검증 호출 실패, JSON 파싱 실패, 상태 누락·비정상 값은 PASS로 전환하지 말라.
- 핵심 법률 주장이 `UNSUPPORTED` 또는 `UNCERTAIN`이면 최종 확정하지 말라.
- 법률 결론은 있는데 주장 추출이 비어 있거나 source ID가 유효하지 않으면 추가 확인 또는 안전 종료로 처리하라.
- PASS는 필요한 모든 검사를 통과한 경우에만 허용하라. 확신도 숫자나 LLM 자기 평가만으로 승인하지 말라.
- 정상적인 근거 기반 답변의 PASS 경로는 유지하라.

### 3.6 제한된 복구와 재검증

복구 가능한 `REVISE`와 `INSUFFICIENT`를 원인에 따라 분기하라. 법령 누락은 원문 검색, 사건 증거 누락은 사실 확인 요청, 단순 답변 오류는 확보한 근거에 따른 재작성으로 연결하라.

복구 후에는 반드시 새 답변을 재검증하라. 검색 성공이나 재작성 완료만으로 PASS를 부여하지 말라. 동일 검색 결과만 반복되면 진행 없음으로 종료하라.

초기 기본 예산은 자동 복구 1회로 두고 기존 공식 검색·승인 경로를 포함한 전체 호출 수와 시간의 상한을 정의하라. `revision_count`의 reducer와 노드 반환값이 중복 가산되지 않도록 통일하라. 실패·거절·예산 소진 시 종료 사유를 남겨라.

재검색 질의에는 핵심 쟁점과 누락 법령을 보존하라. 문자열 길이 제한으로 가장 중요한 누락 지적사항이 잘리지 않게 하라.

### 3.7 최종 답변에서 오류 제거

근거 부족 시 답변 첫 부분에 확정할 수 없는 결론과 이유를 설명하라. 검증된 부분과 추가 확인할 사실·법령을 구분하라.

거절된 법률 주장, 그 주장으로 계산한 날짜 예시, 동일 오류가 포함된 전문가 원문을 최종 상담 답변에 다시 붙이지 말라. 미검증 초안이라는 제목이나 면책 문구만으로 해결된 것으로 보지 말라. 인용 표식 제거와 마크다운 정리는 내용 오류 수정과 다르다.

정답의 기간만 치환하는 방식으로 구현하지 말라. 주택 임대차 질문의 적용 조건과 실제 확보한 특별법 원문에 따라 결론을 결정해야 한다. 원문 미확보 시 모델 기억으로 확정적인 대체 답변을 생성하지 말라.

### 3.8 API·저장·화면·관측성

- 실행 성공과 답변 검증 통과를 분리하라. 기존 API 실행 상태의 호환성을 검토하고 별도 검증 상태·사유·복구 횟수·종료 사유를 제공하라.
- 저장 후 조회, 대화 이력 복원, 승인 후 재개에도 동일한 상태를 유지하라.
- 과거 데이터의 검증 정보 누락은 미확인으로 표시하라. PASS로 추정하지 말라.
- 재검토 예산 소진으로 종료한 `REVISE`를 화면에서 수정 완료로 표시하지 말라.
- 검증 상태와 핵심 주의사항을 사용자가 본문을 읽기 전에 알 수 있게 표시하라.
- 트레이스에 원본·추가·검증·거절 출처 수, 복구 원인과 결과를 기록하라. API Key·개인정보·상담 원문을 추가 노출하지 말라.

## 4. 회귀 테스트와 수용 기준

| 시험 | 필수 기대 결과 |
|---|---|
| 실제 Tool.invoke → Executor → 전문가 → 워크플로우 | 검색 텍스트와 구조화 출처가 모두 도착 |
| 서로 다른 두 요청 동시 실행 | 출처와 상태 혼합 없음 |
| 같은 문서·페이지의 서로 다른 조문 | 양쪽 청크 보존, 반복 검증 후에도 유지 |
| 파일명 동일·페이지 또는 버전 불일치 | 인용 일치 검사에서 거절 |
| 단어는 유사하나 기간·기산점이 다른 주장 | 내용 지지 실패 |
| 민법만 있는 주택 묵시 갱신 질문 | 특별법 필요 감지, 1개월 확정 답변 차단 |
| 필요한 공식 특별법 원문 확보 | 적용 조건에 맞는 답변 생성 후 재검증 |
| 특별법 검색 실패·승인 거절 | 오류 결론 없는 근거 부족 안내 |
| 검증 API·JSON 오류, 상태 누락 | 자동 PASS 없음 |
| 핵심 UNCERTAIN, 법률 주장 목록 비어 있음 | 자동 PASS 없음 |
| 재검색 반복·예산 소진 | 유한 종료, 검증·화면 상태 일치 |
| 오류 결론이 포함된 전문가 원문 | 최종 답변에 재노출되지 않음 |
| 정상적인 충분한 법률 근거 | 정상 PASS와 출처 표시 유지 |
| 저장·조회·승인 후 재개 | 검증 상태·출처·종료 사유 유지 |

네트워크 없는 단위 테스트는 가짜 검색·LLM을 사용해도 되지만 실제 도구 실행 경로를 거쳐라. 공식 법령 fixture의 출처와 버전을 명시하고 실제 서버 재현과 구분하라. 운영 DB를 비우거나 테스트 데이터로 덮어쓰지 말라.

## 5. 구현 순서 및 완료보고

1. 현재 코드와 추가된 테스트를 읽고 미충족 조건을 재현하라.
2. 출처 전달·식별·원본 보존을 수정하라.
3. 공식 원문 확보와 검증 오류 처리, 적용 법령·내용 검증을 보완하라.
4. 복구 예산과 재검증을 연결하고 오류 결론을 최종 답변에서 제거하라.
5. API·저장·화면 상태를 맞춘 뒤 관련 단위·통합 테스트를 실행하라.
6. 가능한 환경에서 동일 질문을 실제 서비스로 재현하고 새 trace와 결과를 보고하라.

완료보고에는 변경 파일과 이유, 실제 실행 명령·결과, 미실행 항목, 실제 원문 확보 여부, 잔여 위험을 적어라. 결과는 `PASS`, `PARTIAL`, `FAIL`, `NOT_TESTED`, `BLOCKED`를 구분하라. 신규·수정 코드의 한국어 주석은 `docs/development/CODING_COMMENT_STANDARD.md`를 따르고 준수 여부를 보고하라.
