[00:42–01:30 | 2장: 핵심 기능]

[02:00–02:40 | 아키텍처의 전체 실행 영역]

[02:40–03:28 | LangGraph를 왜·어떻게 사용하는가]
FastAPI 내부의 Agent Orchestrator는 LangGraph StateGraph입니다. main의 build_legal_graph에는 활성 노드 14개, 시작·종료를 포함한 Edge 30개가 등록되어 있습니다. supervisor_initialize가 사건·증거·대화 상태를 준비하고 route가 분야를 정합니다. run_agents가 법령 검색이나 전문 분석을 수행한 뒤 synthesize에서 초안을 만듭니다. verification은 법령과 사건 사실을 근거로 판단하고 finalize, revise, insufficient 또는 공식 검색 경로로 분기합니다. 검증 실패의 수정 루프는 verification으로 돌아옵니다.

[03:28–04:10 | 일반 상담과 증거 기반 상담의 차이]
모든 요청에 전문 에이전트 여러 개를 실행하지 않습니다. 현재 코드는 문서 기반 상담인 DOCUMENT_MODE이면 분야 분류용 LLM을 건너뛰고, run_agents에서는 전문 Agent 답변 생성보다 법령 근거 확보에 집중합니다. 일반 법률 상담에만 필요한 Specialist가 실행됩니다. 이 설계로 불필요한 분류와 중간 결과 토큰을 줄였습니다. 이 부분은 route_node와 run_agents_node에서 확인할 수 있습니다.

[04:10–04:55 | RAG·데이터·그래프 역할 분리]
PostgreSQL은 사건, 승인된 증거 원문, 사실, 타임라인, 상담 이력의 기준 저장소입니다. 업로드시 파일 SHA-256으로 동일 사건 중복 파일을 차단하고, 상담 중에는 승인 상태와 추출 버전까지 확인합니다. ChromaDB는 임베딩 기반 법령 검색에 사용하고, Neo4j는 증거·사실 관계를 탐색합니다. Graph Sync Worker는 서버 기동시 실행되어 약 5초마다 PostgreSQL의 동기화 작업을 처리합니다. 단, GraphRAG가 생성한 요약을 확정적인 상담 근거로 쓰지 않고 승인된 증거 원문을 우선합니다.

[04:55–05:35 | 외부 서비스와 검증 연결]
Azure OpenAI는 LLM과 임베딩 모델을 제공하며, 실제 배포 모델은 환경변수로 설정합니다. 이번 KPI 비교는 GPT-5.4를 사용했습니다. 추가 공식 법령이 필요할 때만 HITL 승인 흐름에서 OpenLaw API를 호출합니다. Verification은 주요 주장과 인용 출처의 연결, 법령 시행일 및 부칙 적용 가능성을 검사합니다. 검증 당시 초안과 출처가 달라졌는지는 SHA-256으로 확인하여 안전한 최종화와 제한적 검증 재사용에 활용합니다.

Langfuse에는 Node, Tool, LLM 호출, 처리시간과 토큰 사용량을 기록해 성능 병목을 분석합니다. 상담 이외의 대응계획은 별도 업무 처리이며, 법률문서 작성은 Context, Requirements, Generation, Verification, Review Gate로 구성된 별도 LangGraph 워크플로우입니다. 이렇게 실행 제어, 사건 원본 데이터, 검색 지식과 검증을 분리한 것이 아키텍처의 핵심입니다.

[06:00–06:58 | 핵심 기술 난제]
가장 어려웠던 문제는 법령을 잘 찾는 것과 법률적으로 옳게 답하는 것이 서로 다르다는 점, 그리고 검증을 늘릴수록 처리시간과 비용이 급증한다는 점이었습니다. 예를 들어 SC-002에서는 계약 보증금 2억 2천만 원과 실제 반환액 5천만 원, 잔액 1억 7천만 원을 구분해야 합니다. 같은 거래가 계약서나 거래내역에 중복 등장하더라도 반환액을 두 번 합산하면 안 됩니다. 신청만 한 임차권등기와 실제 완료도 구별해야 합니다.

[06:58–07:48 | 시간적 법령 검증]

[07:48–08:38 | 증거 근거·검증 상태 설계]
사건 데이터는 PostgreSQL의 증거 원문을 기준으로 삼습니다. 추출된 사실 후보는 사용자가 승인하되, 승인 자체가 법적 진실을 보증하는 것은 아니므로 Claim 단위 Grounding Verification을 수행합니다. 검증 결과가 PASS이면 답변을 확정하고, REVISE이면 수정 후 재검증합니다. 근거를 확보할 수 없으면 INSUFFICIENT로 판단 유보합니다. 최종 출력 직전에는 답변 해시와 출처 Manifest, 문서의 승인 상태를 다시 확인하여 검증 당시의 내용이 바뀌지 않았는지 점검합니다.

[08:38–09:25 | Self-Correction 최적화와 측정]
초기에는 새 법령이 없는데도 같은 검색과 재작성을 반복하여 상담당 평균 439.15초가 걸렸습니다. 이에 라우팅 Fast-Path를 도입하고, 추가 검색으로 실제 신규 출처가 확보되었는지 확인하였습니다. 질문·초안·출처·검토 기준일이 동일한 경우에만 기존 검증 결과를 제한적으로 재사용하고, 같은 결함이 반복되면 조기 종료했습니다. E2E V8 2차에서는 평균 101.68초, 토큰 66.4% 절감, LLM 비용 71.6% 절감을 측정하였습니다.

[09:25–10:00 | 트레이드오프·확장]
